Periodic Framework — Python API

Write a Python function, name its period and its topics, and TAIL OS runs it on time.

Read this first

  • What you need: the TAIL OS image for QEMU. Its disk image carries Python and the periodic module, so there is nothing to install. import periodic loads the module from the standard library archive /usr/lib/python314.zip. The standard payloads, tail_messages, are a file of their own beside it, /usr/lib/python3.14/tail_messages.py.
  • What you get: a node that runs on a fixed period, reads and publishes topics, and needs no loop, thread, sleep or retry.
  • Time to a first node: one file of 21 lines, written with vi on the booted image and started with python. There is no build.

This page is the Python API. The Rust page describes the Rust API. Both use the same words for the same things. Where the two differ, this page says why.

A node is a function that TAIL OS runs once every period. Each run is a release. The framework runs the timing loop for you: it reads the clock, calls the function, and sleeps for the rest of the period.

A node has inputs, the topics it reads, and outputs, the topics it publishes. You declare each one on the parameter that receives it. Each input has its own freshness bound. A node can also take run-time parameters that you tune from the shell, and serve one action: a goal a client sends it, which takes many releases.

Quick start

counter is one file and one node. It runs every 100 ms, counts its releases, and publishes the count:

# counter.py

from periodic import periodic, publish, run, now, Payload, Skip, Topic

# What the counter publishes on every release: releases run so far, and when this one ran.
Releases = Payload("count:u64 stamp_ns:u64", "Releases")

# The counter's releases, published by the counter alone.
COUNTER_RELEASES = Topic("counter/releases", Releases, lane="kernel")

count = 0


@periodic(every="100ms", on_overrun=Skip)
def counter(releases=publish(COUNTER_RELEASES)):
    global count
    count += 1
    releases.publish(Releases.instance(count=count, stamp_ns=now()))


run()
  • @periodic turns the function into a node, and run() runs it. The file has no loop and no sleep.
  • releases=publish(COUNTER_RELEASES) is the node's output. The value the body hands to releases.publish(..) is published on counter/releases when the body returns.
  • count lives at module level. That is how a Python node keeps state between releases.
  • Releases is a payload, the type a topic carries. Payload lays it out exactly as the same struct in Rust.

Run and check it

Python and the periodic module are on the disk image of the QEMU download. On the booted image, write the file with vi /counter.py, then start it in the background and look at it:

tsh> python /counter.py &
tsh> node list
counter  pid 9  python
tsh> topic echo -n 3 --as "count:u64 stamp_ns:u64" counter/releases
# counter/releases: kernel lane, --as, 16 B, layout 0x79e81151
count=2 stamp_ns=3888115504
count=3 stamp_ns=3988053776
count=4 stamp_ns=4088056880

A Python node takes a few seconds to start while the interpreter loads, so wait a moment before node list. node list shows each running node: its name, its process and its program. Your pid and counts differ.

topic echo reads the topic as any other program would. --as names the payload's fields, because Releases is not a standard payload that topic echo decodes on its own. Each count is one more release. The layout identity, 0x79e81151, is the Rust quick start's, because the two Releases declarations have the same fields. The shell tools page describes both tools.

Your first nodes

The main example is drive, a node that reads two topics and publishes one. A topic is a named channel that carries one payload type. The lane is how a topic's messages travel from publisher to readers (Topics and lanes).

drive reads sensor/range and cmd/velocity and publishes drive/velocity; the other ends can be Rust nodes or Python nodes.

The section shows four programs:

Program What it does
publisher.py publishes one topic
subscriber.py reads one topic
drive.py reads two topics and publishes one
steer.py reads one topic and publishes two

None of them writes a loop or a sleep. None declares a standard payload: each imports it from tail_messages. That module is generated from the Rust robot_messages crate, so a Python node and a Rust node hold one definition. tail_messages is a file on the QEMU image. The Raspberry Pi 3 image built from the BSP does not include Python.

A topic

from tail_messages import Range

# The front ranger's readings, in the `range_front` frame.
SENSOR_RANGE = Topic("sensor/range", Range, lane="safe")

A topic is defined once, with three facts: its name, its payload and its lane. All three belong to the topic, not to a node, because every end of a topic must agree on them. The lane is "kernel", "safe" or "fast", and it has no default. A payload carries no frame: the frame belongs to the topic, and its comment names it.

A Python publisher

examples/publisher.py:

from periodic import periodic, publish, run, monotonic_ns, Skip, Topic
from tail_messages import Range, RANGE_INFRARED

# The front ranger's readings, in the `range_front` frame.
FROM_PYTHON = Topic("pair/from_python", Range, lane="kernel")

count = 0


@periodic(every="20ms", on_overrun=Skip)
def sensor(reading=publish(FROM_PYTHON)):
    global count
    count += 1
    reading.publish(Range.instance(stamp_ns=monotonic_ns(), radiation_type=RANGE_INFRARED,
                                   field_of_view=0.05, min_range=0.02, max_range=4.0,
                                   range=0.25 * count, variance=0.0))


run()

An output is declared on the parameter that publishes it: reading=publish(FROM_PYTHON). On every release the body gets an Out in that parameter. reading.publish(value) hands it the release's value, and the framework publishes it once the body returns. A body returns nothing.

RANGE_INFRARED is one of Range's named values, generated beside it. count keeps state at module level; below is why Python needs no init for that.

Pick the stamp clock by what the node does:

The node Stamps with
reads hardware, like sensor monotonic_ns(): nanoseconds since boot, read when called, the instant it read the device
decides from its inputs now(): the current release's one clock reading in nanoseconds, the instant every input was judged against; 0 before run() has opened the node
passes an input on the input's own stamp_ns

Both read the clock every stamp_ns field is in, the same one as periodic::monotonic_ns() and periodic::now() in Rust. A replay of the node hands the body the recorded now(), so a stamp from now() replays exactly; monotonic_ns() reads anew. See Recording and replay.

A process is one node, so now() takes no argument. Call it from the body: from a thread you started, it raises RuntimeError.

A Python subscriber

The declaration and the fail-safe branch of examples/subscriber.py. The rest of its body counts correct readings and exits with a verdict:

from periodic import periodic, run, subscribe, Skip, Topic
from tail_messages import Range, RANGE_ULTRASOUND

# The front ranger's readings, in the `range_front` frame.
SENSOR_RANGE = Topic("sensor/range", Range, lane="safe")


@periodic(every="20ms", on_overrun=Skip)
def brake(lidar=subscribe(SENSOR_RANGE, stale_after="210ms")):
    global seen
    reading = lidar.get()
    # `get()` is None when nothing has arrived yet and when what last arrived is older than
    # `stale_after`. The two collapse on purpose, so this is the fail-safe branch.
    if reading is None:
        return

An input is declared on the parameter it feeds: lidar=subscribe(SENSOR_RANGE, stale_after="210ms"). On every release the body gets a Cycle in that parameter. stale_after says how old a reading may be before it counts as absent.

A node that reads two topics

examples/drive.py, the whole program. It passes the commanded velocity on while the range reading says the way is clear, and publishes a stop otherwise:

from periodic import periodic, publish, run, subscribe, Skip, Topic
from tail_messages import Range, Twist, Vector3

# Velocity commands, in the `base_link` frame.
CMD_VELOCITY = Topic("cmd/velocity", Twist, lane="kernel")
# The front ranger's readings, in the `range_front` frame.
SENSOR_RANGE = Topic("sensor/range", Range, lane="safe")
# The velocity the drive is given, in the `base_link` frame.
DRIVE_VELOCITY = Topic("drive/velocity", Twist, lane="safe")

STOP_WITHIN_M = 0.3
STILL = Vector3.instance(x=0.0, y=0.0, z=0.0)
STOP = Twist.instance(linear=STILL, angular=STILL)


@periodic(every="20ms", on_overrun=Skip)
def drive(command=subscribe(CMD_VELOCITY, stale_after="310ms"),
          lidar=subscribe(SENSOR_RANGE, stale_after="70ms"),
          velocity=publish(DRIVE_VELOCITY)):
    twist, reading = command.get(), lidar.get()
    if twist is not None and reading is not None and reading.range > STOP_WITHIN_M:
        velocity.publish(twist)
    else:
        # The command or the range is absent or stale, or an obstacle is close.
        velocity.publish(STOP)


run()

Two inputs on two lanes, each with its own bound, and one output. The body gets one Cycle per input and one Out per output, in the order the parameters are written. A command may be 310 ms old and still be used; a range reading only 70 ms.

get() returns None both when nothing has arrived and when what it holds is older than stale_after. So one else branch covers a sensor that goes quiet and a sensor that never came up.

Twist nests two Vector3s, read as twist.linear.x, the name Rust uses. You build a nested payload from instances of the payloads it nests.

Start the nodes in any order. A safe-lane input waits up to ten seconds for its publisher; a kernel-lane input opens at once.

A node that publishes two topics

examples/steer.py, the whole program. It steers towards x = 2 m. It commands a velocity on every release that has a usable odometry reading. On the releases the robot stands still, it also reports where it stopped:

from periodic import periodic, publish, run, subscribe, Payload, Skip, Topic
from tail_messages import Odometry, Twist, Vector3

DriveState = Payload("stamp_ns:u64 x:f64 y:f64", "DriveState")

# The robot's estimated pose and velocity, in the `odom` frame.
ODOMETRY = Topic("odometry", Odometry, lane="safe")
# Velocity commands, in the `base_link` frame.
CMD_VELOCITY = Topic("cmd/velocity", Twist, lane="kernel")
# Where the robot last stood still, in the `odom` frame.
DRIVE_STATE = Topic("drive/state", DriveState, lane="kernel")

GOAL_X_M = 2.0
GAIN_PER_S = 0.5
STILL_BELOW_M_S = 0.01

# Built once and rewritten on every release: an output keeps a reference until the body
# returns, and packs it then.
velocity = Twist.instance(linear=Vector3.instance(x=0.0, y=0.0, z=0.0),
                          angular=Vector3.instance(x=0.0, y=0.0, z=0.0))
stop = DriveState.instance(stamp_ns=0, x=0.0, y=0.0)


@periodic(every="20ms", on_overrun=Skip)
def drive(odometry=subscribe(ODOMETRY, stale_after="50ms"),
          command=publish(CMD_VELOCITY),
          state=publish(DRIVE_STATE)):
    reading = odometry.get()
    if reading is None:
        return                          # absent or stale: neither output publishes
    velocity.linear.x = GAIN_PER_S * (GOAL_X_M - reading.pose.position.x)
    command.publish(velocity)
    if abs(reading.twist.linear.x) < STILL_BELOW_M_S:
        stop.stamp_ns = reading.stamp_ns
        stop.x, stop.y = reading.pose.position.x, reading.pose.position.y
        state.publish(stop)


run()

Each output is its own parameter with its own Out. When the body returns, the framework publishes every output that was handed a value, in the order the outputs are declared: command, then state. The order the body handed them over in does not matter.

An output handed nothing publishes nothing at that release. Its readers keep what it last published: here drive/state holds the last stop. A release with no usable reading publishes neither output.

publish keeps a reference, not a copy, and packs the value when the body returns. So velocity and stop can be built once and rewritten on every release. A change made after publish but before the body returns is published. An output carries one publication per release: a second publish at the same release raises ValueError. DriveState is the example's own payload, declared with Payload (Payloads).

Which examples are tested

All four programs run in the project's tests. publisher.py, subscriber.py, drive.py, steer.py and balance.py (Run-time parameters) also run on the emulated Raspberry Pi 3, each against Rust nodes. None of them has run on real hardware.

Declaring a node

@periodic(every="20ms", on_overrun=Skip)
def drive(command=subscribe(CMD_VELOCITY, stale_after="310ms"),
          lidar=subscribe(SENSOR_RANGE, stale_after="70ms"),
          velocity=publish(DRIVE_VELOCITY)):
    ...

The decorator states what is true of the whole node. Each input, output, run-time parameter and served action is declared on its own parameter, as the parameter's default.

Where Written Required
decorator every="<duration>" always
decorator on_overrun=Skip, CatchUp or Fault always
parameter name=subscribe(TOPIC, stale_after="<duration>") once per input
parameter name=publish(TOPIC) once per output
parameter name=param(default, range=(minimum, maximum)) once per run-time parameter
parameter name=serve(ACTION, lease="<duration>") at most once per node

A node reads, publishes or serves an action. One that does none of them is refused:

NodeError: a periodic node must `publish`, take an input, or serve an action; one that does none of them is a timer, and the framework has nothing to offer it

Every rule on this page is checked at decoration, which is import time: before a topic is opened and before a release is taken. Rust refuses the same mistakes at compile time; import is the earliest point Python has.

The node's keys

@periodic(every="20ms", on_overrun=Skip)

every is the period: the time from one release to the next. Releases fall on start + n * period, so they never drift.

on_overrun says what happens on an overrun, a release whose body runs past the next release: Skip, CatchUp or Fault, imported from periodic. There is no default. The policies are the Rust ones (OverrunPolicy).

NodeError: a periodic node must declare `on_overrun`, one of Skip, CatchUp or Fault; there is no default, because a cycle that misses its deadline is a safety-relevant event and silence is not an answer to it

A duration is an integer and a unit, ns, us, ms or s, with nothing between them (Durations). A mistyped one is refused at decoration, naming the key and, for an input, its topic:

lidar=subscribe(SENSOR_RANGE, stale_after="70 ms")

NodeError: the `stale_after` of topic 'sensor/range' is '70 ms'; write an integer and one of ns, us, ms, s -- as in "20ms". There is no fractional form: write "1500us", not "1.5ms"

Any other key is refused, safety among them (Safety).

A topic

SENSOR_RANGE = Topic("sensor/range", Range, lane="safe")

lane is "kernel", "safe" or "fast" (Topics and lanes says which to choose). It has no default. A topic without one can be constructed, and subscribe and publish refuse it:

NodeError: topic 'sensor/range' needs its lane: where the topic is defined, write Topic('sensor/range', Range, lane="kernel"), or "safe", or "fast". The lane belongs to the topic -- both ends must use the same one -- and it has no default

Define a topic in a module both programs import, so its two ends cannot be written differently. Two separate definitions, or one in Python and one in Rust, are compared by the payload's size and layout identity (Payloads). A payload with two fields exchanged is refused.

The lane is not compared. A Python reader that writes lane="kernel" for a topic its Rust writer defines on the safe lane starts and receives nothing, and neither side is told. The Rust page lists every lane mismatch and what it does.

An input

lidar=subscribe(SENSOR_RANGE, stale_after="70ms")

The parameter is one input: the topic, then stale_after, how old a reading may be before this node reads it as absent. On every release the body is handed a Cycle in that parameter. These are the words of the Rust attribute, #[subscribe(TOPIC, stale_after = "..")], in the one place Python offers beside a parameter.

  • Every input needs both parts. There is no default bound and no node-wide bound.
  • Each input has its own bound. Two nodes may read one topic with different bounds.
  • At each release the framework reads the clock once and judges every input against its own stale_after at that one reading, so two inputs never disagree about the time.
Written NodeError
subscribe(SENSOR_RANGE) the input on topic 'sensor/range' must declare `stale_after`; without it there is no answer to "is this data still usable", and the node would act on whatever it was last given
subscribe("sensor/range", stale_after="70ms") a topic is a definition, not a name: define TOPIC = Topic('sensor/range', YourPayload, lane="safe") once, and write subscribe(TOPIC, stale_after="<duration>")
subscribe(SENSOR_RANGE, stale_after="70ms", lane="safe") `lane` is not an input key: the lane belongs to the topic. Write Topic("some/name", YourPayload, lane="safe") where the topic is defined
lidar=SENSOR_RANGE `drive` parameter `lidar` names topic 'sensor/range' but not whether the node reads or publishes it: write `lidar=subscribe(TOPIC, stale_after="<duration>")` to read it, or `lidar=publish(TOPIC)` to publish it

Sizing stale_after. Use the Rust page's rule:

stale_after >= (lost publications tolerated + 1) x the publisher's period + this node's period

Then move it half a node period off, never onto a multiple of the node's period. drive.py runs every 20 ms and tolerates one lost reading from a 20 ms sensor: 2 x 20 + 20 = 60, written "70ms". Nothing checks the rule. A bound shorter than the node's period is accepted, and makes the input usable only on the release a publication arrives.

The bound is measured from receipt at this node. The data may be older by the gap since the node's previous release, which is one period unless a release ran late.

A node reads a topic once. Two inputs that name one topic are refused, naming both:

NodeError: `drive` inputs `front` and `rear` name the same topic 'sensor/range': a node reads a topic once

An output

velocity=publish(DRIVE_VELOCITY)

The parameter is one output. publish takes the topic and nothing else; the lane is the topic's. On every release the body is handed an Out in that parameter:

Call Effect
velocity.publish(value) Hands the output this release's value, an instance of the topic's payload. A reference is kept, not a copy
velocity.publish(None), or no call Nothing is published on that output at this release
a second velocity.publish(...) in one release ValueError: output 'drive/velocity' was already published at this release; an output carries one publication per release
  • Nothing is sent at the call. When the body returns, every output holding a value is packed and published, in the order the outputs are declared. A served action's status goes out after them.
  • A body that raises publishes nothing at that release. The exception leaves run().
  • An output handed nothing publishes nothing. Its readers go on holding what it last published. That is not an overrun.

A body returns nothing. The output is the parameter, never the return value. The first release whose body returns a value stops the node:

NodeError: `drive` returned Twist, and a node publishes through its outputs, not its return value. Declare one on a parameter, output=publish(TOPIC), write output.publish(value) where `drive` returned the value, and return nothing

A node publishes a topic once. Two outputs that name one topic are refused, naming both:

NodeError: `drive` outputs `front` and `rear` name the same topic 'drive/velocity': a node publishes a topic once

One node may name the same topic as an input and as an output. Each release then reads what an earlier release published.

A refused publish does not stop the node. When the transport refuses a publication, nothing is raised. The other outputs are still published, and the node goes on. The sixteenth refusal in a row on one output writes one record to the console:

drive: 16 consecutive publishes to drive/state refused (Refused); still trying

A publish the transport takes ends the run, and so does a release that hands that output nothing. A refused value is not sent again. A Rust node writes the same record to its log ring; a Python node writes it to the console, so logview does not show it.

What the body may look like

run() calls the body with one argument per parameter, positionally, in the order they are written: a Cycle for an input, an Out for an output, the value in force for a run-time parameter, the node's Goal for a served action. So every parameter must be one of the four.

Written NodeError
def drive(gain, lidar=subscribe(...)) `drive` parameter `gain` is not fed by anything. A parameter of a periodic body is an input, `gain=subscribe(TOPIC, stale_after="<duration>")`, an output, `gain=publish(TOPIC)`, a run-time parameter, `gain=param(<default>, range=(<min>, <max>))`, or a served action, `gain=serve(ACTION, lease="<duration>")`
def drive(*readings) `drive` takes `*readings`, and a periodic body is called with exactly one argument per declared input or parameter: ...
def drive(**options) `drive` takes `**options`, and a periodic body is called positionally and is never passed a keyword. Remove `**options`
async def drive(...) `drive` is declared `async def`, so calling it would return a coroutine and run nothing. A periodic body is an ordinary function, called once per release; remove `async`
a body that contains yield `drive` contains `yield`, so calling it would return a generator and run nothing. ...
  • A method is declared bound to its object: periodic(every="10ms", on_overrun=Skip)(Estimator().step), as in Cycle. Its first parameter receives the object. @periodic on a method inside its class body is refused, with this bound form as the fix.
  • A wrapper made by another decorator, around the function that declares the inputs or run-time parameters, is refused: what it wraps declares them, not the wrapper. Put @periodic directly on the function that declares them.
  • A body called by hand finds its parameters still holding their declarations. Using one as a Cycle raises a NodeError that says run() is what calls a periodic body.

Three differences from Rust, each deliberate

Rust Python Why
A topic's payload and lane read from the topic's type arguments of Topic Python has no type to read them from
A mistyped duration builds, and the node stops at start-up NodeError at decoration decoration runs before anything is opened
safety a key refused a Python node is Quality Managed by design (Safety); nothing keeps it off the fast lane

A declaration in the earlier grammar

Before a node could read and publish several topics, subscribe, stale_after, lane, payload and publish were keys of @periodic. A declaration that still writes one is refused with one message. It lists every such key, says where each went, and prints the declaration as it is written now, with its own values:

`sensor` is declared in an earlier grammar: `publish` is no longer a key of @periodic.

    publish      an output is declared on the parameter that publishes it

Written as it is now, this declaration is:

    OUTPUT = Topic('pair/from_python', Range, lane='kernel')

    @periodic(every='20ms', on_overrun=Skip)
    def sensor(output=publish(OUTPUT)):
        ...
        output.publish(value)    # the value `sensor` returned

Paste it, and give the output a name of your own. A body that already declares its parameters in the current form and still carries an old key is told to remove the key.

A node that converts

Each topic names its own payload, so a node that reads one payload and publishes another needs nothing special:

from periodic import periodic, publish, run, subscribe, Skip, Payload, Topic

Range = Payload("stamp:u64 range_mm:u32 quality:u32", "Range")        # 16 bytes
Distance = Payload("mm:u32", "Distance")                              # 4 bytes

PILOT_RANGE = Topic("pilot/range", Range, lane="safe")
PILOT_ECHO = Topic("pilot/echo", Distance, lane="safe")


@periodic(every="20ms", on_overrun=Skip)
def bridge(lidar=subscribe(PILOT_RANGE, stale_after="210ms"), echo=publish(PILOT_ECHO)):
    reading = lidar.get()
    if reading is None:
        return
    echo.publish(Distance.instance(mm=reading.range_mm))


run()

Run-time parameters

from periodic import param, periodic, publish, run, subscribe, Skip, Topic
from tail_messages import Imu, Twist, Vector3

# The IMU's readings, in the `imu_link` frame.
IMU_DATA = Topic("imu/data", Imu, lane="safe")
# Velocity commands, in the `base_link` frame.
CMD_VELOCITY = Topic("cmd/velocity", Twist, lane="kernel")

STILL = Vector3.instance(x=0.0, y=0.0, z=0.0)
STOP = Twist.instance(linear=STILL, angular=STILL)
forward = Twist.instance(linear=Vector3.instance(x=0.0, y=0.0, z=0.0), angular=STILL)


@periodic(every="20ms", on_overrun=Skip)
def balance(imu=subscribe(IMU_DATA, stale_after="70ms"),
            command=publish(CMD_VELOCITY),
            kp=param(42.0, range=(0.0, 200.0)),
            enabled=param(True)):
    reading = imu.get()
    if not enabled or reading is None:
        command.publish(STOP)   # disabled from the shell, or the IMU is absent or stale
        return
    forward.linear.x = kp * reading.angular_velocity.y
    command.publish(forward)


run()

A parameter is a value you tune while the node runs: a gain, a limit, a flag. You declare it on the argument that receives it, with param(default, range=(minimum, maximum)). The body is handed each value by value on every release, and reading one costs nothing. examples/balance.py is the whole program above.

Rule Detail
Name The argument's name, at most 23 bytes.
Kind The default's type: bool, int (held as a 64-bit integer) or float (a 64-bit float).
range A tuple of two numbers, both ends included. Required for int and float; a bool takes none: param(True). An int parameter's bounds are ints; a float parameter's may be either.
Count At most 16 parameters per node.

Change one from the shell

param writes a request; the node applies it and answers with its state.

tsh> param list balance
kp      = 42.0  (0.0 .. 200.0)
enabled = true
tsh> param set balance kp 45.5
balance: kp = 45.5 from release 112
tsh> param set balance kp 250
param: balance kp = 250.0 is outside 0.0 .. 200.0; nothing was set
tsh> param set balance enabled false
balance: enabled = false from release 140
tsh> param list balance
kp      = 45.5   (0.0 .. 200.0, default 42.0)
enabled = false  (default true)
tsh> param list
balance  2 parameters

The release numbers are illustrative.

  • A set takes effect at the start of a release. The release that param set names is the first whose body gets the new value, counting from 0 at the node's first release. A body never sees a value change while it runs.
  • param set reports success only when the node answers. It exits 1 when the node refuses, or does not answer within eight of its periods plus 250 ms.
  • Set coupled values in one command. param set balance kp 50 enabled true is one request, applied whole at one release. Two commands are two requests, applied at two releases.
  • The node checks every request against the declared range, both ends included, whoever sent it. It refuses a value outside the range, a NaN, or an unknown name, and nothing changes. param refuses the same values before it sends.
  • Values last for the node's life. A restart starts at the defaults again. To keep a value, change its default in the source; param list shows each changed value beside its default.
  • Every Python node with parameters is settable. There is no safety key, so nothing marks a node whose configuration must not change at run time. Give such a node no parameters, and its values as constants.
  • param logs each applied change in its own ring of the system log: balance: kp 42.0 -> 45.5 from release 112 (logview -s param).
  • Replay hands each body the values it ran with (Recording and replay).
  • node list shows every node; param list shows only nodes with parameters. node info balance prints what the node declares.

What parameters cost

  • One non-blocking read per release, of the request topic, made by run() before the body. Almost always it finds nothing. A release that finds a request also checks up to 16 values and publishes the node's state. All of it counts inside the release that overrun accounting measures.
  • No allocation on a release without a change. The body's arguments are rebuilt only on a release whose values differ from the previous release's (Cost).
  • Two kernel-lane topics per node, <node>/__params and <node>/__param_set, named after the decorated function. Count them in the image's topic budget, as the Rust page gives it.
  • Without those topics the node runs on its defaults and cannot be set. This happens when topic storage is full, for example. The node says so once, on the console:
balance: no parameter topics (topic storage full); runs with its defaults
  • The first request may be slow. The interpreter is loaded from the disk, so the code that handles a request may be paged in from the file system during the release that handles the first one.
  • Any program can set a parameter, within its range, by writing the request topic, as any program can publish any kernel-lane topic. A value outside the range never reaches a body.

Actions

The client sends a goal; the node answers with a status on every release.

An action is a request that takes many releases: "drive to (2.0, 0.5)", "home the arm", "dock". A client sends a goal. The node accepts or refuses it at once, reports feedback on every release, and ends it with a result. The client can cancel it. The node stops it on its own when the client is gone.

It is the mechanism of the Rust page's actions. Either language serves either: a Python node serves a Rust client, and a Python client sends to a Rust node.

Define the action once, in a module the node and its clients import:

# robot_actions.py
from periodic import Action, Payload

# Where to drive, in the `odom` frame [m]; how far the base still has to go [m]; where it
# stopped, in the `odom` frame [m].
DriveTo = Payload("x:f64 y:f64", "DriveTo")
DriveProgress = Payload("remaining_m:f64", "DriveProgress")
DriveDone = Payload("x:f64 y:f64", "DriveDone")

# Drive the base to a point.
DRIVE_TO = Action("drive_to", DriveTo, DriveProgress, DriveDone)

The name and the three payloads belong to the action. When a Rust definition of drive_to meets this one, the framework compares them payload by payload. Two that disagree are refused, never misread.

Action(...) raises NodeError at the definition for any of these:

  • a goal larger than 4072 bytes;
  • a feedback and a result that together pass 3920 bytes, each rounded up to 8;
  • a name longer than 246 bytes.

The programs in this section show the whole surface. They are not run as shown, but a node and a client of every form here run on the emulated Raspberry Pi 3 in the project's tests.

Serving it

A node serves an action on one more parameter, serve(ACTION, lease=...):

import math

from periodic import periodic, publish, run, serve, subscribe, Skip, Topic
from robot_actions import DRIVE_TO, DriveDone, DriveProgress
from tail_messages import Odometry, Twist, Vector3

# The base's odometry, `base_link` in `odom`.
ODOMETRY = Topic("odometry", Odometry, lane="safe")
# Velocity commands, in the `base_link` frame.
CMD_VELOCITY = Topic("cmd/velocity", Twist, lane="kernel")

ARRIVED_WITHIN_M = 0.05
STILL = Vector3.instance(x=0.0, y=0.0, z=0.0)
STOP = Twist.instance(linear=STILL, angular=STILL)
command = Twist.instance(linear=Vector3.instance(x=0.0, y=0.0, z=0.0), angular=STILL)
progress = DriveProgress.instance(remaining_m=0.0)


@periodic(every="20ms", on_overrun=Skip)
def drive(odometry=subscribe(ODOMETRY, stale_after="50ms"),
          velocity=publish(CMD_VELOCITY),
          goal=serve(DRIVE_TO, lease="100ms")):
    active, reading = goal.active(), odometry.get()
    if active is None or reading is None:
        velocity.publish(STOP)  # no goal, cancelled, its client gone, or odometry stale
        return
    target, here = active.goal, reading.pose.position
    progress.remaining_m = math.hypot(target.x - here.x, target.y - here.y)
    if progress.remaining_m < ARRIVED_WITHIN_M:
        active.succeed(DriveDone.instance(x=here.x, y=here.y))
        velocity.publish(STOP)
        return
    active.feedback(progress)
    command.linear.x = min(0.5, progress.remaining_m)     # your control law
    velocity.publish(command)

  • The status follows the outputs. The node publishes one status per release, idle included, after all its outputs. A client that sees a goal stopped knows the stop went out first.
  • A node serves at most one action. A second serve(...) parameter raises NodeError.

The lease

The lease is how long a goal survives without a keep-alive from its client. The handle sends a keep-alive once per server period while you use it: iterating it, wait, cancel, or poll once per release. When the keep-alives stop, the node stops the goal at the end of the lease, and the goal ends 'abandoned'. That covers a client that was killed, crashed, hung, or simply stopped using its handle.

  • The lease is required and must be at least twice the period. Both are checked when @periodic runs:

    Written NodeError
    goal=serve(DRIVE_TO) action 'drive_to' is served with no lease: write serve(ACTION, lease="<duration>"). A goal whose client has gone is stopped when its lease runs out, so the lease is what stops the robot, and it has no default
    goal=serve(DRIVE_TO, lease="39ms") at every="20ms" `drive` serves action 'drive_to' with lease '39ms', shorter than twice the period '20ms': a lease of two periods lets a client be one period late, and about five is the advice
    goal=DRIVE_TO `drive` parameter `goal` names action 'drive_to' but not its lease: write `goal=serve(ACTION, lease="<duration>")`

  • Choose about five periods, for example lease="100ms" on a 20 ms node. That rides out a lost keep-alive, a client one period late, and a client node up to four periods slow.

  • A killed client's goal stops within the lease plus two periods. At 20 ms and 100 ms that is about 140 ms after the last keep-alive, plus release lateness. No death signal stops it sooner.

  • A periodic client slower than the lease loses every goal. It polls once per its own release. A client every 150 ms against a 100 ms lease sees each goal end 'abandoned'. Make the lease longer than the slowest client's period plus one server period.

  • A program that stops using its handle loses its goal. In drive = DRIVE_TO.send(goal); long_work(); drive.wait(), the goal is abandoned during long_work. Iterate the handle, or call poll or wait, while the goal should run.

What it costs and what it takes

  • At most eight requests read and one status published per release, idle releases included. Both count inside the cycle that overrun accounting measures.
  • No allocation per release. The Goal, its ActiveGoal and the goal's object are built once, before the first release. A client's poll that takes no feedback allocates nothing.
  • Two kernel-lane topics per action, <action>/__goal and <action>/__status. Count them in the image's topic budget.
  • Replay hands each body the goal it ran with, and arrived() as recorded. In a replay, feedback, succeed and abort keep their checks and publish nothing.
  • Any program can send, keep, cancel or replace a goal by writing the request topic with another process's id. No topic has writer authorisation yet. The lease, and the device's own lease, remain the stop.

You record a run, then run one node of it again, offline, against exactly what it saw. Here /drive.py is the obstacle stop of your first nodes. lidar and joystick stand for whatever publishes sensor/range and cmd/velocity; the counts are illustrative.

Nothing in the node changes. It needs no line of code for replay: run() reads the options, and replay reads the node's release journal. The lines are the ones a Rust node's replay prints. The mechanism is the Rust page's recording and replay.

Start the publishers too. run() waits up to ten seconds for a publisher of each safe-lane input (run()). Without one, run() raises OSError, and the node records nothing.

The release journal

The record of release k goes out before the body runs.

Every node with an output publishes one record per release on a kernel-lane topic of its own, <function name>/__releases: drive publishes drive/__releases. You write nothing for it. A node with no output has no journal.

Record k is the one a Rust node of the same declaration publishes, and it carries the same facts (the Rust page's release journal): the release, each input, each parameter, the goal, and release k-1's outputs.

  • One kernel-lane publish per release, of at most 4096 bytes, before the body. It counts inside the cycle that overrun accounting measures.
  • One topic per node with an output in the image's topic budget: one page for a record up to 192 bytes, two up to 384 bytes.

When the journal cannot be opened, the node runs and publishes exactly as it would with one. It says so once on the console:

drive: no release journal (topic storage full); this run cannot be replayed

Every node, with an output or not, also publishes its description on <function name>/__node, for node list. That is one more topic in the budget. When it cannot be opened, the node runs unlisted and says so once:

drive: no node description (topic storage full); node list does not show this node

A node's function name must be unique within an image, as in Rust: two nodes of one name share one journal topic.

Why not a struct format string. struct pads with native alignment only under @. Under <, >, = and ! it packs tight. What Payload(..) refuses

A declaration a Rust payload could not have is refused where it is written, with what to do. Take the row that matches what you wrote:

Written in Payload(.., "Refused") NodeError

Padding is refused because a gap would carry the sender's uninitialised bytes. A field name must be usable in every language the payload is declared in, so a keyword such as from is refused.

Both ends must hold one definition

Payload(..) computes the payload's layout identity: a 32-bit hash of the canonical text, which covers the field names, their order, their types, nesting, array lengths and named values. It is the identity the Rust derive computes for the same fields. On every lane, the size and the identity are checked against the other end when the topic opens. A node whose payload disagrees does not start: run() raises an OSError naming the topic.

Here a node's payload disagrees with the one the kernel topic range/front carries. On kernel, the reason and the console record end with what the topic carries:

could not start: topic `range/front` refused the open: this is not the payload type the topic carries: it carries 32-byte payloads of layout 0x6772d100

So two declarations with the same fields in another order are refused, in Python and Rust alike.

Not compared: the payload's name (Point read as Vector3 is admitted, because the bytes are the same three f64), a field's unit, and the lane.

A kernel topic lives while an end holds it. Once every end of the old payload has closed, the corrected declaration creates the topic anew.

missed() publications the lane lost for this input since the previous release
rejected() publications the lane refused on this input since the previous release
overruns() releases the node missed since its previous release ran
is_healthy() True when missed(), rejected() and overruns() are all zero

get()

reading = lidar.get()
if reading is None:
    velocity.publish(STOP)   # absent or stale

Returns the sample if one was received and is no older than stale_after. A stale sample returns None, the same as no sample, so the fail-safe branch is the default branch.

get() borrows. It returns the same object on every release, with its fields rewritten. That mirrors Rust's get() -> Option<&T>. A body that keeps the object and reads it on a later release sees new data. Rust's borrow checker catches that mistake; Python cannot, so it is stated here. The Cycle objects are also the same ones on every release.

This reuse is what keeps a release free of allocations the garbage collector has to walk (Cost).

copied()

self.last_reading = lidar.copied()

Returns the same sample in a new object you own. Use it to keep a sample past this release.

arrived()

wheels = odometry.get()
if odometry.arrived() and wheels is not None:
    self.pose.x_mm = wheels.travelled_mm   # once, on the release it arrives

True if a newer publication was taken at this release. get() answers "is there a usable reading?"; arrived() answers "is it new?". A node fed by a slower input sees a usable reading on every release and a new one on some.

topic()

if lidar.get() is None:
    print(f"no usable reading on {lidar.topic()}")

Returns the name of the topic this input reads: "sensor/range". A parameter's name is only its author's choice; topic() is the binding itself.

since_received()

gap = lidar.since_received()
if gap is not None and gap > 0.040:
    raise_sensor_warning()

Returns the seconds since a publication last arrived at this node, as a float. It is not the publication's age: no lane timestamps a publication. It is None until something arrives, and exactly zero on the release arrived() is true.

was_stale()

if lidar.was_stale():
    print("using fail-safe: last reading too old")

True if a sample was received and has aged past stale_after. Use it only when you need the difference that get() hides.

Limit: never received is never stale. An input that has received nothing returns False, however long the node has run. stale_after is not a start-up deadline. A node that must act when a publisher never comes up tests get() is None, which covers "not yet" and stale alike.

missed()

if lidar.missed() > 0:
    dropped += lidar.missed()

Returns the publications the lane lost for this input since the previous release. It is not a running total. Each lane counts its own losses:

Lane missed() counts
kernel publications the topic overwrote before the node read them, counted from the input's open. The topic keeps at least its newest 8.
safe, fast publications the lane itself reports skipped

Limit: missed() == 0 does not mean the node saw every publication. An input is handed the newest publication at each release. The ones a newer one replaced are handed to nobody and are not counted.

rejected()

if lidar.rejected() > 0:
    rejected_total += lidar.rejected()

Returns the publications the lane refused on this input since the previous release. It is not a running total. On kernel it is always 0, because a publisher of another payload is refused when it opens (Payloads).

overruns()

if lidar.overruns() > 0:
    velocity.publish(last_command)

Returns the releases the node missed since its previous release ran. It is one count for the node, the same on every input of a release. Read it from any one input; adding them up counts each overrun once per input.

Limit: a Python node writes no overrun record to the system log. A node with no input has no Cycle to read the count from. So under Skip or CatchUp, the body of a Python node that only publishes cannot observe its overruns.

is_healthy()

if not lidar.is_healthy():
    raise_degraded()

True if this input saw no loss, no rejection and no overrun on this release: missed(), rejected() and overruns() all zero, in one call.

An input is a value, the newest one

examples/estimator.py reads a 10 ms IMU and a slower wheel odometry. It predicts on every release and applies the odometry correction once, on the release it arrives:

from periodic import periodic, publish, run, subscribe, Skip, Payload, Topic

Imu = Payload("yaw_rate_mrad_s:i32 forward_mm_s2:i32", "Imu")
Odometry = Payload("travelled_mm:i64 heading_mrad:i32 reserved:u32", "Odometry")
Pose = Payload("x_mm:i64 heading_mrad:i32 corrections:u32", "Pose")

IMU_DATA = Topic("imu/data", Imu, lane="safe")
WHEEL_ODOMETRY = Topic("wheel/odometry", Odometry, lane="safe")
ESTIMATE_POSE = Topic("estimate/pose", Pose, lane="safe")


class Estimator:
    """A dead-reckoned heading, corrected by the wheels whenever they report."""

    def __init__(self):
        self.pose = Pose.instance(x_mm=0, heading_mrad=0, corrections=0)

    def step(self,
             imu=subscribe(IMU_DATA, stale_after="35ms"),
             odometry=subscribe(WHEEL_ODOMETRY, stale_after="65ms"),
             estimate=publish(ESTIMATE_POSE)):
        """Predict from the IMU, correct from the wheels when they report, publish the pose."""
        rates = imu.get()
        if rates is None:
            return                                # no usable IMU: publish nothing this cycle
        self.pose.heading_mrad += rates.yaw_rate_mrad_s // 100
        wheels = odometry.get()
        if odometry.arrived() and wheels is not None:
            self.pose.x_mm = wheels.travelled_mm  # once, on the cycle the reading arrives
            self.pose.heading_mrad = wheels.heading_mrad
            self.pose.corrections += 1
        estimate.publish(self.pose)


periodic(every="10ms", on_overrun=Skip)(Estimator().step)

The payloads here are the example's own, not the standard ones from tail_messages. This file runs on the development host only, against a stand-in for the transport.

A node behind a faster publisher is handed the newest publication at each release. So a topic that carries increments must not be read as an input: the increments the node passed over are lost, and missed() does not count them. The odometry above is a cumulative reading for that reason.

run()

run()

run() runs the declared node. It does not return until the node's policy stops it.

When the command line ends in --replay FILE [--life N], run() replays the node instead and never returns. The process ends inside it, after the last release or at a refused replay (Recording and replay).

run() What it means for you
reads the whole of sys.argv as it is when run() is called, and uses only the trailing --replay .. part a script that consumes its own arguments by rewriting sys.argv first hands over what is left
flushes sys.stdout and sys.stderr before it opens the node and before every release, skipping one that is None what the body printed is written before any call that may end the process
refuses a second declared node, naming both a process is one node, as a Rust node is one program

The decorator cannot run the node itself. A module whose import never finishes is never entered into sys.modules, and every traceback from it would be reported inside an import.

The order it opens topics in

open outputs, in declaration order -> open inputs, in parameter order -> gc.freeze() -> release 0

run() opens the topics the node publishes first, in the order they are declared. Then it opens its inputs, in the order the parameters are written.

Input's lane When nobody publishes it yet
safe, fast the node waits, for ten seconds in all: one wait for the node, not one per topic
kernel the node never waits: the input is admitted with no publisher and reads "not yet" until one publishes

While the node waits for a later input, it holds nothing. What was published meanwhile is dropped at the first release.

The node starts at its first release, not when run() opens its topics. Whatever was published before that is thrown away unread: when it was received is not known, and it must not be presented as fresh. The time between opening the topics and the first release, gc.freeze() included, is not charged to the node as overruns.

Limit: an input reads "not yet" on the first release, unless another program published in the instant between that discard and the release's own read.

Safety

A Python node cannot declare a topic safety-relevant, and this is deliberate.

@periodic(every="20ms", on_overrun=Fault, safety=True)

NodeError: a Python node cannot declare `safety`, and this is deliberate.

A safety classification asserts that a bound on cycle time exists and is known. The garbage collector's pauses, measured on the emulated Raspberry Pi 3:

Collection Pause
A full collection, against a bare interpreter heap 6.6 ms worst, 4.4 ms median
An incidental collection inside a 20 ms release grid 2.5 ms: 12.7% of the period

Both the pause and its frequency scale with your live heap, which the framework neither observes nor bounds. There is no bound to assert, so the claim is not available to make.

A Python node is Quality Managed by construction, as the fast lane is by its own design.

Cost

Measured on the emulated Raspberry Pi 3, on a node with one input. These are not board numbers: the emulator's CPU is not a Raspberry Pi 3's. Use the ratios to budget, not the absolute milliseconds.

Cost How much
Smallest period with no overruns 5 ms; at 1 ms the node overran 35 releases in 200
Lateness against the grid median about 0.9 to 1.0 ms, p99 about 1.7 ms, at every period
Time to the first release cold about 4.2 s, warm about 1.4 to 1.9 s
Allocations the collector walks, per release none, whatever the number of inputs

The time to the first release matters to a system integrator: a Python node is not ready for seconds after it is spawned. That time is interpreter start-up. The node's ten-second admission wait already spans it, so a Python subscriber may still be started before its Rust publisher.

What the framework does about the collector

You do not have to do any of this yourself:

  • run() calls gc.freeze() before the first release. That moves the interpreter's whole start-up heap out of the generations the collector walks. A full collection costs 6.6 ms before that call and 0.018 ms after it.
  • Nothing the collector walks is allocated per release. The Cycle objects, the sample each get() returns and the payload buffers are created once.
  • A node's run-time parameters are handed over in one argument tuple. It is built at the first release, and rebuilt only on a release whose values differ from the previous release's. Every other release makes nothing for them.

What you can do

A body that does not keep what it makes triggers no collection at all: CPython collects on allocations minus deallocations. Keeping a rolling window of samples is what makes the collector run. If you need one, that is the cost to measure.

Glossary

action: a request that takes many releases, such as "drive to (2.0, 0.5)": a client sends a goal, and the serving node reports feedback on every release and ends it with a result.

frame (coordinate frame): one of the robot's coordinate systems. Frame sets and their lookup are Rust only in this release; a Python node uses the conventions in tail_messages.

goal: one request of an action, sent by a client and handed to the serving node's body on every release until it ends.

input: a topic a node reads, declared on a parameter with subscribe(TOPIC, stale_after=".."); the body is handed a Cycle there.

lane: how a topic's messages travel, written in the topic's definition: "kernel" copies through the kernel (up to 4 writers, 4 KiB), "safe" shares memory with one writer and may carry safety data, "fast" shares memory with one writer and may not.

layout identity: a 32-bit hash of a payload's fields, their order and types, which Payload(..) computes as the Rust derive does; an end whose identity differs from the topic's is refused at open.

lease: how long a served goal lives without its client's keep-alive, at least twice the period, after which the node ends the goal abandoned.

node: a function, or a bound method, given to @periodic(..), whose body run() calls once on every release.

output: a topic a node publishes, declared on a parameter with publish(TOPIC); the body is handed an Out there, and what it hands out.publish(..) is published when the body returns.

overrun: a release that runs past the next one; on_overrun says what happens then.

parameter: a run-time parameter, a value declared with param(default, range=(minimum, maximum)) that the shell can change while the node runs.

payload: the type a topic carries, a standard tail_messages record or your own declared with Payload("fields", "Name").

period: the interval every sets; releases fall on start + n * period.

release: one scheduled instant on the period's grid, at which the body runs once.

release journal: the record every node that publishes writes on <function name>/__releases at every release, which replay reads.

replay: running one node again, offline, against a recording, with --replay FILE at the end of its command line, and comparing its outputs with the recorded ones.

stale_after: an input's bound on how old a sample may be, measured from receipt at this node, before it reads as absent.

topic: a named channel that carries one payload type on one lane, defined once with Topic(name, payload, lane=..).
