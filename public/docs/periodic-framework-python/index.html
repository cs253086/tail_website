Periodic Framework — Python API

Declare a period; the framework owns the timing loop, topic admission, freshness and the publish point. A node is a function with a decorator — there is no loop to write.

This is the Python half of the Rust API. The words mean the same things and are spelled the same way, so a reader of that page already knows this one. Where the two differ, this page says why.

A node reads as many topics as its body has inputs, each with its own bound, takes any run-time parameters an operator tunes from the shell while it runs, serves at most one action -- a goal a client sends it, which takes many releases -- and publishes as many topics as its body has outputs, each on the releases the body chooses.

Quick start

One file, one node. counter runs every 100 ms, counts its releases, and publishes the count:

# counter.py

from periodic import periodic, publish, run, now, Payload, Skip, Topic

# What the counter publishes on every release: releases run so far, and when this one ran.
Releases = Payload("count:u64 stamp_ns:u64", "Releases")

# The counter's releases, published by the counter alone.
COUNTER_RELEASES = Topic("counter/releases", Releases, lane="kernel")

count = 0


@periodic(every="100ms", on_overrun=Skip)
def counter(releases=publish(COUNTER_RELEASES)):
    global count
    count += 1
    releases.publish(Releases.instance(count=count, stamp_ns=now()))


run()

@periodic turns the function into a node, and run() runs it: the framework owns the loop, the timing and the publish, so the file has no loop and no sleep. The node's output is the parameter releases=publish(COUNTER_RELEASES); whatever the body hands releases.publish(..) is published on counter/releases when the body returns. count lives at module level, which is how a Python node keeps state between releases. Releases is a payload of this program's own, laid out exactly as the same struct in Rust.

Run and check it

Python and the periodic module are on the disk image of the QEMU download; there is nothing to install. On the booted image, write the file with vi /counter.py, start it in the background and look at it:

tsh> python /counter.py &
tsh> node list
counter  pid 9  python
tsh> topic echo -n 3 --as "count:u64 stamp_ns:u64" counter/releases
# counter/releases: kernel lane, --as, 16 B, layout 0x79e81151
count=2 stamp_ns=3888115504
count=3 stamp_ns=3988053776
count=4 stamp_ns=4088056880

A Python node takes a few seconds to start, while the interpreter loads, so give it a moment before node list. node list shows every running node: its name, its process and its program; the pid and the counts on your system differ. The layout identity is the Rust quick start's, because the two Releases declarations have the same fields. topic echo reads the node's topic as any other program would; --as tells it the payload's fields, since Releases is not one of the standard payloads it decodes on its own. Each count is one more release. The shell tools page describes both tools.

Your first nodes

Four programs: a node that only publishes, a node that reads one topic, a node that reads two, and a node that publishes two. None writes a loop or a sleep, and none declares a payload: each imports the standard ones from tail_messages, which the build prints from the Rust crate robot_messages, so a Python node and a Rust node hold one definition.

import periodic loads the module from /usr/lib/python314.zip, and tail_messages is a file of its own on the image, /usr/lib/python3.14/tail_messages.py, printed by the image build. The Raspberry Pi 3 image built from the BSP does not include Python.

These are tested examples. Each runs on the development host in the project's tests, and publisher.py, subscriber.py, drive.py and balance.py (Run-time parameters) also run on the emulated Raspberry Pi 3, each against Rust nodes, and so does steer.py, the node with two outputs. Nothing here ran on real hardware.

A topic

from tail_messages import Range

# The front ranger's readings, in the `range_front` frame.
SENSOR_RANGE = Topic("sensor/range", Range, lane="safe")

A topic is defined once: its name, the payload it carries, and the lane that carries it. All three belong to the topic and not to a node, because every end of a topic must agree on them and one node may touch several topics that differ in each. A payload carries no frame: the frame belongs to the topic, and its comment says which.

A Python publisher

examples/publisher.py:

from periodic import periodic, publish, run, monotonic_ns, Skip, Topic
from tail_messages import Range, RANGE_INFRARED

# The front ranger's readings, in the `range_front` frame.
FROM_PYTHON = Topic("pair/from_python", Range, lane="kernel")

count = 0


@periodic(every="20ms", on_overrun=Skip)
def sensor(reading=publish(FROM_PYTHON)):
    global count
    count += 1
    reading.publish(Range.instance(stamp_ns=monotonic_ns(), radiation_type=RANGE_INFRARED,
                                   field_of_view=0.05, min_range=0.02, max_range=4.0,
                                   range=0.25 * count, variance=0.0))


run()

An output is declared on the parameter that publishes it: reading=publish(FROM_PYTHON). On every release the body is handed an Out in that parameter, and reading.publish(value) hands it the release's value; the framework publishes it once the body returns. A body returns nothing. count lives at module level, which is one way a Python node keeps state between cycles; below is why Python needs no init for that. monotonic_ns() is the stamp clock: nanoseconds since boot on the counter the node's releases are placed on, the clock every stamp_ns field is in, and the same one periodic::monotonic_ns() reads in Rust. RANGE_INFRARED is one of Range's named values, generated beside it.

There are two ways to read that clock, and they differ in a replay:

Call What it returns In a replay Stamp with it
monotonic_ns() the counter, read when called a new reading, so what it stamps diverges a measurement, when it is taken: this sensor node
now() the release's reading: the instant every input of the release was judged against; 0 before run() has opened the node the recorded reading, so what it stamps replays exactly a value the node decides from its inputs

now() is periodic::now() in Rust. A process is one node, so it takes none. Call it from the body: from a thread you started it raises RuntimeError.

A Python subscriber

The declaration and the fail-safe branch of examples/subscriber.py. The rest of that file's body counts correct readings and exits with a verdict, so the test can judge it by its exit status:

from periodic import periodic, run, subscribe, Skip, Topic
from tail_messages import Range, RANGE_ULTRASOUND

# The front ranger's readings, in the `range_front` frame.
SENSOR_RANGE = Topic("sensor/range", Range, lane="safe")


@periodic(every="20ms", on_overrun=Skip)
def brake(lidar=subscribe(SENSOR_RANGE, stale_after="210ms")):
    global seen
    reading = lidar.get()
    # `get()` is None when nothing has arrived yet and when what last arrived is older than
    # `stale_after`. The two collapse on purpose, so this is the fail-safe branch.
    if reading is None:
        return

An input is declared on the parameter it feeds: lidar=subscribe(SENSOR_RANGE, stale_after="210ms"). On every release the body is called with a Cycle in that parameter.

A node that reads two topics

examples/drive.py, the whole program. An obstacle stop: it passes the commanded velocity on while a range reading says the way is clear, and publishes a stop otherwise.

from periodic import periodic, publish, run, subscribe, Skip, Topic
from tail_messages import Range, Twist, Vector3

# Velocity commands, in the `base_link` frame.
CMD_VELOCITY = Topic("cmd/velocity", Twist, lane="kernel")
# The front ranger's readings, in the `range_front` frame.
SENSOR_RANGE = Topic("sensor/range", Range, lane="safe")
# The velocity the drive is given, in the `base_link` frame.
DRIVE_VELOCITY = Topic("drive/velocity", Twist, lane="safe")

STOP_WITHIN_M = 0.3
STILL = Vector3.instance(x=0.0, y=0.0, z=0.0)
STOP = Twist.instance(linear=STILL, angular=STILL)


@periodic(every="20ms", on_overrun=Skip)
def drive(command=subscribe(CMD_VELOCITY, stale_after="310ms"),
          lidar=subscribe(SENSOR_RANGE, stale_after="70ms"),
          velocity=publish(DRIVE_VELOCITY)):
    twist, reading = command.get(), lidar.get()
    if twist is not None and reading is not None and reading.range > STOP_WITHIN_M:
        velocity.publish(twist)
    else:
        # The command or the range is absent or stale, or an obstacle is close.
        velocity.publish(STOP)


run()

Twist nests two Vector3s, read as twist.linear.x, the name Rust uses; a nested payload is built from instances of the payloads it nests.

Two inputs on two lanes, each with its own bound, and one output. The body is called with one Cycle per input and one Out per output, in the order the parameters are written.

get() returns None both when nothing has arrived and when what is held is older than that input's stale_after. The two collapse on purpose, so the fail-safe branch is the branch that runs when a sensor goes quiet, and the one that runs when it never came up.

On QEMU, with the range topic silenced and the command still published, the test saw this node's first stop 81 to 102 ms after the last range publication, over six runs; the window it asserts is over 70 ms and at most 70 ms plus two periods plus a 200 ms band. The command was passed on again when the range returned.

Each node waits for its topics for up to ten seconds, so it may start before or after the nodes at its other ends.

A node that publishes two topics

examples/steer.py, the whole program. A steering step towards x = 2 m: it commands a velocity on every release it has a usable odometry reading, and on the releases the robot stands still it also reports where it stopped.

from periodic import periodic, publish, run, subscribe, Payload, Skip, Topic
from tail_messages import Odometry, Twist, Vector3

DriveState = Payload("stamp_ns:u64 x:f64 y:f64", "DriveState")

# The robot's estimated pose and velocity, in the `odom` frame.
ODOMETRY = Topic("odometry", Odometry, lane="safe")
# Velocity commands, in the `base_link` frame.
CMD_VELOCITY = Topic("cmd/velocity", Twist, lane="kernel")
# Where the robot last stood still, in the `odom` frame.
DRIVE_STATE = Topic("drive/state", DriveState, lane="kernel")

GOAL_X_M = 2.0
GAIN_PER_S = 0.5
STILL_BELOW_M_S = 0.01

# Built once and rewritten on every release: an output keeps a reference until the body
# returns, and packs it then.
velocity = Twist.instance(linear=Vector3.instance(x=0.0, y=0.0, z=0.0),
                          angular=Vector3.instance(x=0.0, y=0.0, z=0.0))
stop = DriveState.instance(stamp_ns=0, x=0.0, y=0.0)


@periodic(every="20ms", on_overrun=Skip)
def drive(odometry=subscribe(ODOMETRY, stale_after="50ms"),
          command=publish(CMD_VELOCITY),
          state=publish(DRIVE_STATE)):
    reading = odometry.get()
    if reading is None:
        return                          # absent or stale: neither output publishes
    velocity.linear.x = GAIN_PER_S * (GOAL_X_M - reading.pose.position.x)
    command.publish(velocity)
    if abs(reading.twist.linear.x) < STILL_BELOW_M_S:
        stop.stamp_ns = reading.stamp_ns
        stop.x, stop.y = reading.pose.position.x, reading.pose.position.y
        state.publish(stop)


run()

Each output is its own parameter, handed its own Out. When the body returns, the framework publishes every output that was handed a value, in the order the outputs are declared -- command, then state -- whatever order the body handed them over in. An output handed nothing publishes nothing at that release, and its readers go on holding what it last published: here drive/state carries the last stop, and a release with no usable reading publishes neither.

velocity and stop are built once and rewritten on every release. publish keeps a reference, not a copy, and the value is packed when the body returns, so changing an object after handing it over publishes the changed value. DriveState is the example's own payload, declared with Payload (Payloads).

Declaring a node

The node's keys

Key
every required Release period: "20ms". Releases fall on start + n * period, never drifting
on_overrun required Skip, CatchUp or Fault. No default

Nothing about an input or an output is a node key: each is declared on its parameter. publish= was a key of @periodic while a node published its return value; it is refused now, with the declaration rewritten (below).

A topic

Topic(name, payload, lane=...), with lane one of "kernel", "safe" or "fast".

The lane has no default. A topic written without one can be constructed and cannot be used: subscribe and publish refuse it, saying where to write it.

Define a topic in a module both programs import, so its two ends cannot be written differently. Two definitions written separately, or one in Python and one in Rust, are compared by the payload's size and by the identity of its layout (see Payloads), so a payload with two fields exchanged is refused. The lane is not compared. Failing case: a Python reader that says lane="kernel" for a topic its Rust writer defines on the safe lane is admitted at once and then receives nothing, and neither side is told.

An input

name=subscribe(TOPIC, stale_after="<duration>"), as the default of the parameter it feeds. They are the same words as the Rust attribute, #[subscribe(TOPIC, stale_after = "..")], in the one position Python offers beside a parameter.

stale_after is this node's bound for this input: how long the topic may stay silent before the node stops using what it last read. Two nodes may read one topic with different bounds, and one node gives each of its inputs its own.

Sizing it. The age a node sees is a whole number of its own periods, give or take the wake-up jitter, so a bound that is a multiple of the period is decided by microseconds. Write it half a period off:

stale_after >= (publications you tolerate losing + 1) x the publisher's period
               + this node's period

drive.py runs every 20 ms. Its range bound tolerates one lost reading from a 20 ms sensor: 2 x 20 + 20 = 60, written "70ms". Nothing checks the rule. A bound shorter than the node's period is accepted, and makes the input usable only on the cycle a publication arrives.

What the bound guarantees. It bounds how long ago this node received the data. The data may be older by the time it waited to be read: up to the gap since the node's previous cycle, which is one period unless a cycle ran late.

A node reads a topic once. Two parameters that name one topic are refused at decoration, naming both:

`drive` inputs `front` and `rear` name the same topic 'sensor/range': a node reads a topic once

A topic a node publishes may also be one of its inputs: the node then reads its own previous publication.

An output

name=publish(TOPIC), as the default of the parameter that publishes it. The same words as the Rust attribute, #[publish(TOPIC)], in the position Python offers beside a parameter. publish takes the topic and nothing else; the lane is the topic's.

On every release the body is handed an Out in that parameter:
out.publish(value) Hands the output this release's value, an instance of the topic's payload. A reference is kept, not a copy
a second out.publish(...) in one release ValueError: output 'cmd/velocity' was already published at this release; an output carries one publication per release
out.publish(None), or no call Nothing is published on that output at this release

The publish point is when the body returns. Then every output holding a value is packed and published, in the order the outputs are declared, and emptied. A body that raises publishes nothing at that release, on any output. A served action's status goes out after all of them.

A body returns nothing. A body that returns a value is refused at that release with a NodeError that names the output form:

`drive` returned Twist, and a node publishes through its outputs, not its return value. Declare one on a parameter, output=publish(TOPIC), write output.publish(value) where `drive` returned the value, and return nothing

A node publishes a topic once. Two outputs that name one topic are refused at decoration, naming both:

`drive` outputs `front` and `rear` name the same topic 'sensor/range': a node publishes a topic once

A refused publish does not stop the node. When the transport refuses a publication, nothing is raised: the outputs after it are still published at that release, and the node goes on to the next. Refusals are counted per output, and the sixteenth in a row on one output writes one record to the console, naming the node and the topic:

drive: 16 consecutive publishes to drive/state refused (Refused); still trying

A publish the transport takes ends the count, and so does a release that does not publish that output. This is what a Rust node does, in the same words; a Rust node writes the record to its log ring, and a Python node to the console, so logview does not show it. A refused value is not sent again at a later release.

What the body may look like

run() calls the body positionally, with one argument per parameter, in the order the parameters are written -- a Cycle for an input, an Out for an output, the value in force for a run-time parameter, the node's Goal for a served action -- and nothing else. So every parameter is one of the four, and everything that would let a signature take an argument the loop does not pass, or lose one it does, is refused at decoration:

The body
has a parameter with none of a subscribe(...), a publish(...), a param(...) or a serve(...) default refused, naming the parameter
returns a value refused when it does, with a NodeError: what a node publishes it hands to an output
has a keyword-only parameter, *args or **kwargs refused, naming it
is async def, or contains yield refused: calling it would run nothing
is a wrapper around the function that declares the inputs or the run-time parameters, such as one taking *args, **kwargs refused on its own signature, and told why: the inputs and run-time parameters declared on the wrapped function are not parameters of the wrapper. Put @periodic directly on the function that declares them
is a wrapper that takes nothing (made with functools.wraps), around a function that declares an input or a run-time parameter refused, naming the one it does not take: nothing would open the input or hand the parameter a value
is a bound method accepted. Its first parameter receives its object and is not an input, an output or a run-time parameter
is a method decorated inside its class refused, with the bound form to write instead

A node that publishes and reads nothing takes only its outputs; it may still take run-time parameters. A node must publish, read, or serve an action; one that only serves is no timer, since it publishes its action's status on every release.

A body called by hand, without arguments, finds its parameters still holding their declarations. Using one as a Cycle raises a NodeError that says so: run() is what calls a periodic body. A param(...) declaration used as a number raises CPython's own TypeError.

Every one of these is checked when the function is decorated, which is import time, before a topic is opened and before a release is taken. Rust refuses them at compile time; import is the earliest equivalent Python has.

Three differences from Rust, each deliberate

A topic names its own payload. Rust reads the payload and the lane from the topic's type; Python has no type to read them from, and a transport cannot carry a shape nobody named. So both are arguments of Topic.

Durations are checked at decoration. A mistyped every or stale_after is a NodeError before anything is opened, naming the key and, for an input, its topic. In Rust the same mistake builds and stops the node at start-up.

There is no safety key. Asking for one is an error, and this is a design position and not an omission — see Safety. Nothing keeps a Python node off the fast lane.

A declaration in the earlier grammar

Before a node could read several topics, subscribe, stale_after, lane and payload were keys of @periodic, and before it could publish several, so was publish. A declaration that still writes one is refused at decoration with one message that lists every such key it used, says where each went, and prints the declaration as it is written now, with its own values. A publisher in the earlier form:

`sensor` is declared in an earlier grammar: `publish` is no longer a key of @periodic.

    publish      an output is declared on the parameter that publishes it

Written as it is now, this declaration is:

    OUTPUT = Topic('pair/from_python', Range, lane='kernel')

    @periodic(every='20ms', on_overrun=Skip)
    def sensor(output=publish(OUTPUT)):
        ...
        output.publish(value)    # the value `sensor` returned

The rewrite names the output output; give it a name of your own. A body that already declares its inputs with subscribe(...), or run-time parameters with param(...), which the earlier grammar did not have, and has such a key left over is told to remove the key; for publish, also where the output goes: Remove `publish` from @periodic, add the parameter output=publish(TOPIC) for topic 'pilot/echo', and write output.publish(value) where `bridge` returned the value.

A node that converts

Each topic names its own payload, so a filter reading 16 bytes and publishing 4 is ordinary:

  pilot/range               pilot/echo
  Range { stamp: u64,  ──►  Distance { mm: u32 }
          range_mm: u32,
          quality: u32 }
  16 bytes                  4 bytes

This node runs on the emulated Raspberry Pi 3 in the project's tests, between a Rust publisher and a Rust subscriber:

from periodic import periodic, publish, run, subscribe, Skip, Payload, Topic

Range = Payload("stamp:u64 range_mm:u32 quality:u32", "Range")        # 16 bytes
Distance = Payload("mm:u32", "Distance")                              # 4 bytes

PILOT_RANGE = Topic("pilot/range", Range, lane="safe")
PILOT_ECHO = Topic("pilot/echo", Distance, lane="safe")

@periodic(every="20ms", on_overrun=Skip)
def bridge(lidar=subscribe(PILOT_RANGE, stale_after="200ms"), echo=publish(PILOT_ECHO)):
    reading = lidar.get()
    if reading is None:
        return
    echo.publish(Distance.instance(mm=reading.range_mm))

run()

Hand the output nothing to publish nothing this cycle; that is not an overrun. This node's bound is on a multiple of its period: the test is older than the sizing rule and kept its bound when its grammar was migrated.

Run-time parameters

A value you tune while the node runs -- a gain, a limit, a flag -- is a run-time parameter. Declare it on the parameter that receives it, with param(default, range=(minimum, maximum)). examples/balance.py, the whole program:

from periodic import param, periodic, publish, run, subscribe, Skip, Topic
from tail_messages import Imu, Twist, Vector3

# The IMU's readings, in the `imu_link` frame.
IMU_DATA = Topic("imu/data", Imu, lane="safe")
# Velocity commands, in the `base_link` frame.
CMD_VELOCITY = Topic("cmd/velocity", Twist, lane="kernel")

STILL = Vector3.instance(x=0.0, y=0.0, z=0.0)
STOP = Twist.instance(linear=STILL, angular=STILL)
forward = Twist.instance(linear=Vector3.instance(x=0.0, y=0.0, z=0.0), angular=STILL)


@periodic(every="20ms", on_overrun=Skip)
def balance(imu=subscribe(IMU_DATA, stale_after="70ms"),
            command=publish(CMD_VELOCITY),
            kp=param(42.0, range=(0.0, 200.0)),
            enabled=param(True)):
    reading = imu.get()
    if not enabled or reading is None:
        command.publish(STOP)   # disabled from the shell, or the IMU is absent or stale
        return
    forward.linear.x = kp * reading.angular_velocity.y
    command.publish(forward)


run()
  • Each parameter is one line of the signature. Its name is the parameter's name, at most 23 bytes; its kind is its default's type: a bool, an int (held as a 64-bit integer) or a float (a 64-bit float). range is a tuple of two numbers and includes both ends; an int parameter's bounds are ints, and a float parameter's may be either. A bool takes no range: param(True). At most 16 parameters per node. All of it is checked when the function is decorated, with what to write instead.
  • The body is handed the value in force, by value, on every release: reading one costs nothing, and a value never changes while the body runs.
  • The command is one object, rewritten in place and handed to the output on every release, so a release allocates nothing for it (Cost).

From the shell, with param:

tsh> param list balance
kp      = 42.0  (0.0 .. 200.0)
enabled = true
tsh> param set balance kp 45.5
balance: kp = 45.5 from release 112
tsh> param set balance kp 250
param: balance kp = 250.0 is outside 0.0 .. 200.0; nothing was set
tsh> param set balance enabled false
balance: enabled = false from release 140
tsh> param list
balance  2 parameters
tsh> node list
balance  pid 9  python

param list names the nodes that declare parameters; node list names every running node, whatever it declares, with its process and program (the pid is illustrative); node info balance prints what the node declares.

  • A set takes effect at the start of a release. The release param set names is the first whose body is handed the new value, releases being counted from 0 at the node's first. A set made before the first release is handed to the first.
  • Set coupled values in one command. param set balance kp 50 enabled true is one request, handed to the body whole at one release; two commands are two releases.
  • The node checks every request, against its declared range, exactly, both ends included, whoever sent it: a value outside it, a NaN or a name the node does not declare is refused and nothing changes. param refuses the same way before it sends.
  • Values live for the node's life. A restart starts at the defaults again; to keep a value, change its default in the source.
  • Every Python node with parameters is settable. There is no safety key (see Safety), so nothing marks a node whose configuration must not change at run time: give such a node no parameters, and its values as constants.
  • Each applied change is in the system log, written by param, balance: kp 42.0 -> 45.5 from release 112. The node's release journal records the values every release was handed, so a recording shows the releases a change reached, and a replay hands each release its recorded values (Recording and replay).

What it costs and what it takes:

  • One non-blocking read per release, of the node's request topic, made by run() inside its wait for the release, inside the cycle the overrun accounting measures. A release that finds a request also checks at most 16 values and publishes the node's state.
  • The body's arguments are one tuple, built at the first release and built again only on a release whose values differ from the previous release's, with the new values' objects. A set that applies the values already in force changes nothing, and neither does a refused one. Every other release allocates nothing for the parameters. A node without parameters does none of this, and is handed its arguments as before.
  • Two kernel-lane topics per node with parameters, <node>/__params and <node>/__param_set, named after the decorated function: count them in the image's topic budget. When they cannot be opened -- the topic storage is used up, say -- the node runs on its defaults, which nothing can set, and says so once on the console, in this record:
balance: no parameter topics (topic storage full); runs with its defaults
  • The interpreter is loaded from the disk, so a Python node's request handling, which is in the interpreter, may be faulted in from the file system on the release that handles its first request. A Python node is Quality Managed for the reason Safety gives, and this is one more release whose time it does not bound.
  • Any program can set a parameter, within its declared range, by writing the request topic, as any program can publish any kernel-lane topic today.

A declaration that breaks a rule is refused at decoration, naming the function, the parameter and the rule:

Declaration NodeError
mode=param("fast") `balance` parameter `mode` has default 'fast', a str; a parameter's default is a bool, an int or a float
kp=param(42.0) `balance` parameter `kp` is a float parameter and declares no range: a value a shell can set needs its limits, kp=param(42.0, range=(<min>, <max>))
armed=param(True, range=(False, True)) `balance` parameter `armed` is a bool parameter, whose only values are False and True: remove `range`
kp=param(42.0, range=[0, 200]) `balance` parameter `kp` has range [0, 200]; write a pair of numbers, range=(<min>, <max>)
kp=param(250.0, range=(0.0, 200.0)) `balance` parameter `kp`'s default 250.0 is outside its range 0.0 .. 200.0
max_torque_newton_metres=param(..) `balance` parameter `max_torque_newton_metres` is 24 bytes long; a parameter's name is at most 23

The node also refuses a range that is empty, a bound that is not finite, an int that does not fit 64 bits, and a seventeenth parameter, each with its own message.

Actions

A request that takes many releases -- "drive to (2.0, 0.5)", "home the arm", "dock" -- is an action. A client sends a goal; the node accepts or refuses it at once, reports feedback on every release, and ends it with a result. The client can cancel it, and the node stops it on its own when the client is gone. It is the same mechanism as the Rust one (the Rust page's Actions), and any client may talk to any server: a Python node serves Rust clients, and a Python client sends to a node written in Rust.

  client                                     node, every 20 ms
  DRIVE_TO.send(goal) ──── SEND ───────────► release k: goal.active() is the goal, arrived()
          ◄──────── status, feedback ─────── release k, k+1, ...: active.feedback(...)
  keep-alive every server period ──────────►
  drive.cancel()  ──────── CANCEL ─────────► release k': goal.active() is None -> your stop
          ◄──────── status: cancelled ────── (the stop was published before this status)

The programs below are written for this page and show the whole surface; they are not compiled or run as shown. A server and a client of every form shown here run on the emulated Raspberry Pi 3 in the project's tests.

Define the action once, in a module the server and its clients import. Its name and its three payloads -- the goal, the feedback, the result -- belong to it, and a Rust definition of the same action is compared with this one, payload by payload, when its topics are opened: two that disagree are refused, never misread.

# robot_actions.py
from periodic import Action, Payload

# Where to drive, in the `odom` frame [m]; how far the base still has to go [m]; where it
# stopped, in the `odom` frame [m].
DriveTo = Payload("x:f64 y:f64", "DriveTo")
DriveProgress = Payload("remaining_m:f64", "DriveProgress")
DriveDone = Payload("x:f64 y:f64", "DriveDone")

# Drive the base to a point.
DRIVE_TO = Action("drive_to", DriveTo, DriveProgress, DriveDone)

Serve it on one more parameter, with serve(ACTION, lease=...). The body is handed the node's Goal on every release, and goal.active() is the goal the release runs, or None:

import math

from periodic import periodic, publish, run, serve, subscribe, Skip, Topic
from robot_actions import DRIVE_TO, DriveDone, DriveProgress
from tail_messages import Odometry, Twist, Vector3

# The base's odometry, `base_link` in `odom`.
ODOMETRY = Topic("odometry", Odometry, lane="safe")
# Velocity commands, in the `base_link` frame.
CMD_VELOCITY = Topic("cmd/velocity", Twist, lane="kernel")

ARRIVED_WITHIN_M = 0.05
STILL = Vector3.instance(x=0.0, y=0.0, z=0.0)
STOP = Twist.instance(linear=STILL, angular=STILL)
command = Twist.instance(linear=Vector3.instance(x=0.0, y=0.0, z=0.0), angular=STILL)
progress = DriveProgress.instance(remaining_m=0.0)


@periodic(every="20ms", on_overrun=Skip)
def drive(odometry=subscribe(ODOMETRY, stale_after="50ms"),
          velocity=publish(CMD_VELOCITY),
          goal=serve(DRIVE_TO, lease="100ms")):
    active, reading = goal.active(), odometry.get()
    if active is None or reading is None:
        velocity.publish(STOP)  # no goal, cancelled, its client gone, or odometry stale
        return
    target, here = active.goal, reading.pose.position
    progress.remaining_m = math.hypot(target.x - here.x, target.y - here.y)
    if progress.remaining_m < ARRIVED_WITHIN_M:
        active.succeed(DriveDone.instance(x=here.x, y=here.y))
        velocity.publish(STOP)
        return
    active.feedback(progress)
    command.linear.x = min(0.5, progress.remaining_m)     # your control law
    velocity.publish(command)


run()
goal / active
goal.active() The goal this release runs, as an ActiveGoal, or None: idle, and from the release at which a cancel, the client's absence past the lease, or a newer goal of the same client is read. The cases collapse on purpose, as an input's absent and stale readings do, so the stop is the branch you write anyway
active.goal The goal. Borrowed, as Cycle.get()'s sample is: the same object, rewritten
active.arrived() Whether this is the goal's first release: reset your controller here
active.feedback(value) This release's feedback. The last call in a release wins; it is published after your outputs
active.succeed(result) Ends the goal with its result. goal.active() is None from then, this release included
active.abort(code) Ends the goal with code, an int from 0 to 4294967295. At its first release, arrived(), the client is told it was refused with the code instead: this is how a node refuses a goal by its content, with everything its release can see

active is this release's: the same object comes back at every release that runs a goal, and stands for whichever goal that is. Ask goal.active() at every release rather than keep one. A call on it at a release that runs no goal, or after succeed or abort, raises NodeError, where Rust refuses to build it. Call it from the body: from a thread you started, feedback, succeed and abort raise RuntimeError, whatever the node is doing, because the node runs on the thread that called run() and is reached from no other.

Send a goal from a program. The happy path is one line:

done = DRIVE_TO.send(DriveTo.instance(x=2.0, y=0.5)).wait()

With feedback and a cancel:

from periodic import GoalError
from robot_actions import DRIVE_TO, DriveTo

with DRIVE_TO.send(DriveTo.instance(x=2.0, y=0.5)) as drive:   # GoalError('busy' | 'refused', code)
    for progress in drive:                                      # one per server release, until it ends
        print(f"{progress.remaining_m:.2f} m to go")
        if bumper_pressed():
            drive.cancel()                                      # returns once the server has stopped it
    try:
        done = drive.wait()
    except GoalError as ended:
        print(f"drive_to: {ended}")                             # "cancelled"
A goal's handle
ACTION.send(goal) Sends the goal and waits until the server has accepted or refused it: up to ten seconds for a server to appear, so a client may start before its server, then two of its periods. Raises GoalError for a goal that was not accepted
ACTION.start(goal) Returns at once; the goal is sent and answered through poll. What a periodic node uses
poll() Never waits: Progress.Pending, Progress.Running or Progress.Ended. Sends the keep-alive that is due, and takes a new feedback into feedback
feedback The newest feedback the handle was handed, by poll or by iterating it; None until one was
iterating it Each feedback once, waiting for the next, until the goal ends
wait() Waits for the end: the result, or GoalError saying how it ended
cancel() Cancels, and returns once a status shows the goal stopped: the server's stop was published before that status
close(), the end of a with block, the last reference released A goal that has not ended is cancelled

Every feedback and result a handle hands over is an object of its own, which you may keep. A handle keeps its goal alive only while it is used: iterating it, wait and cancel keep it while they wait, and a periodic node calls poll once per release. A handle left unused for longer than the lease has its goal stopped by the server, 'abandoned'.

A client that is itself a periodic node starts a goal and polls it, and never waits:

from periodic import periodic, run, subscribe, Progress, Skip, Topic
from robot_actions import DRIVE_TO
from tail_messages import Range

# The front ranger's readings, in the `range_front` frame.
SENSOR_RANGE = Topic("sensor/range", Range, lane="safe")

STOP_WITHIN_M = 0.3
drive = None


@periodic(every="50ms", on_overrun=Skip)
def patrol(front=subscribe(SENSOR_RANGE, stale_after="120ms")):
    global drive
    reading = front.get()
    if reading is None or reading.range < STOP_WITHIN_M:
        drive = None    # releasing a goal that has not ended cancels it
        return
    if drive is None or drive.poll() is Progress.Ended:
        drive = DRIVE_TO.start(next_waypoint())


run()

The lease is how long a goal runs on once its client stops keeping it: a client killed, hung or simply gone keeps it no more, so the lease is what stops the robot, and it has no default. It is at least twice the node's every, refused at decoration otherwise, which lets a client be one period late. About five periods is the advice -- lease="100ms" at every="20ms" -- which survives a lost keep-alive and a period of lateness, and a client node up to four periods slow.

  • A killed client's goal is stopped within the lease and about two periods: L + 2T and the release's lateness and work, about 140 ms at 20 ms and 100 ms. No signal of a process's death reaches a node, so one period is not reachable.
  • A periodic client keeps its goal once per its own release when it is slower than the server. One slower than the lease less a period loses every goal to 'abandoned', at once and safely; the library cannot know your period, so size the server's lease above the slowest client's period.
  • One goal runs at a time. A new goal from the process whose goal runs replaces it -- the old ends 'preempted', the new one runs from the same release with no stop between -- and a goal from any other process is refused 'busy'. There is no queue.
  • Any program can forge a client's keep-alive or cancel, as any program can write any kernel-lane topic today. A forged keep-alive keeps an abandoned goal alive; the device's own lease stays the safety stop.
  • A served goal is recorded. The node's release journal holds the goal every release ran and whether it arrived, so a replay hands each release its recorded goal.active() and arrived(). In a replay feedback, succeed and abort keep their checks and publish nothing (Recording and replay).

Errors.
GoalError('busy') Another process's goal runs. From send
GoalError('refused', code) The server's body refused the goal at its first release, with code. From send
GoalError('aborted', code) The body ended the goal with code. From wait
GoalError('canceled'), ('preempted'), ('abandoned') Cancelled; replaced by a newer goal of this process; stopped because its keep-alives lapsed past the lease. From wait
GoalError('lost') No longer running, and how it ended was not seen. From send, wait or cancel
GoalError('no_server') No server answered within ten seconds. From send, or from wait after start
OSError from send or start A topic refused the client: a server that holds another definition of the action, or no seat free. The console says which

GoalError has .reason and .code, 0 unless the server gave one. A definition or a declaration that breaks a rule is a NodeError where it is written, naming it:

Written NodeError
Action("drive_to", DriveTo, Big, DriveDone) with a 4073-byte goal action 'drive_to' has a goal of 4073 bytes; a goal is at most 4072, since its record adds 24 bytes and the kernel lane carries 4096
goal=serve(DRIVE_TO) action 'drive_to' is served with no lease: write serve(ACTION, lease="<duration>"). A goal whose client has gone is stopped when its lease runs out, so the lease is what stops the robot, and it has no default
goal=serve(DRIVE_TO, lease="39ms") at every="20ms" `drive` serves action 'drive_to' with lease '39ms', shorter than twice the period '20ms': a lease of two periods lets a client be one period late, and about five is the advice
two parameters with serve(...) `drive` parameter `dock` serves a second action: a node serves one, which `goal` already does
goal=DRIVE_TO `drive` parameter `goal` names action 'drive_to' but not its lease: write `goal=serve(ACTION, lease="<duration>")`

What it costs. Two kernel-lane topics per served action, <action>/__goal and <action>/__status: count them in the image's topic budget. At every release, inside run()'s wait and the cycle the overrun accounting measures, run() reads at most eight requests and publishes one status after your outputs, idle releases included. The Goal, its ActiveGoal and the goal's object are built once, before the heap is frozen, and a release keeps nothing for the action; a client's poll that takes no feedback makes nothing.

Recording and replay

Record a run, then run one node of it again, offline, through its own body, handing each release exactly what that release was handed live:

tsh> topic record -o /rec/py_replay.mcap &              FIRST: before the nodes
tsh> twist_publisher &                                  any program publishing a Twist on replay/cmd
tsh> lidar & python replay_py_watch.py &
     ... the run; then stop the nodes, then the recorder ...
tsh> python replay_py_watch.py --replay /rec/py_replay.mcap
replay: replay_py_watch life 1: 497 releases, 496 compared, identical
facts: replay/range: 19 releases without an arrival, 245 missed, 0 rejected; replay/cmd: 0, 1, 0; 1 overruns
replay: running release 496, the life's last; its output is in no record

The lines are the ones a Rust node's replay prints, from the same code; the program names and counts here are illustrative. replay_py_watch.py is a node that reads replay/range and replay/cmd, and nothing in it was written for replay beyond leaving the trailing arguments alone: its own reading of sys.argv[1] takes --replay there as no word (Writing a node that replays). A node journals and replays as it is, and so does every example on this page that publishes. python drive.py --replay /rec/run.mcap replays the drive of your first nodes.

twist_publisher stands for whatever publishes the node's commands. The node reads replay/cmd on the safe lane, and run() waits up to ten seconds for a safe-lane input's publisher (run()): without one, run() raises OSError and nothing is recorded. Any program that publishes a Twist on replay/cmd serves.

The release journal

Every node that publishes journals each release on a kernel-lane topic of its own, <function name>/__releases: replay_py_watch/__releases, drive/__releases. run()'s wait for release k publishes record k before the body runs, after it read the inputs, handled a parameter request and read the action's requests:

 release k:   wait: sleep -> read the inputs -> parameters, goal -> publish record k
              body(...)
              publish each output handed a value -> lane, and a copy into the next record
 release k+1: wait: ... -> publish record k+1, which carries release k's outputs

Record k holds release k's index and clock reading, the overruns, each input's facts and reading, the parameter values and the goal release k was handed, and the value each output published at release k-1, or zeros where it published none. It is the record a Rust node of the same declaration publishes (the Rust page's release journal), and run() writes it.

What it costs and what it takes: one kernel-lane publish per release, of at most 4096 B, inside run()'s wait and the cycle the overrun accounting measures, and one topic per node that publishes in the image's topic budget (one page for a record up to 192 B, two up to 384 B). When it cannot be opened -- the topic storage is used up, say -- the node runs and publishes as it would with one, cannot be replayed, and says so once on the console:

replay_py_watch: no release journal (topic storage full); this run cannot be replayed

Every node, whatever it declares, also announces itself once to node list, on a kernel-lane topic of its own, <function name>/__node, opened last, after the journal: one more topic per node in the image's budget. When it cannot be opened the node runs, unlisted, and says so once on the console:

replay_py_watch: no node description (topic storage full); node list does not show this node

Replaying

Add --replay FILE at the end of the node's command line, and --life N after it to pick a later life (the node started again begins life 2):

python node.py [ARGS...] --replay FILE [--life N]

run() reads only that trailing part of sys.argv. The module's code runs as in a live run; then run():

Live Replay
opening admits the topics, up to ten seconds reads the file and checks the life; opens no topic of any kind
each release sleeps to the release, reads the inputs never sleeps; compares release k-1's outputs with record k, then hands out record k
an input's Cycle the newest publication the recorded reading, its age and staleness judged by this script's stale_after at the recorded clock reading
overruns(), parameters, goal.active() as they happen as recorded; Fault never stops it
now() the release's clock reading the recorded one
out.publish(value) published when the body returns captured when the body returns and sent nowhere; compared at the next release's wait, with record k+1, so the last release's is never compared (The end of a replay)

A difference names the release, the output by its topic and its first differing byte. replay_py_watch.py altered names the release after its own in its tally from release 50 on:

tsh> python replay_py_watch.py altered --replay /rec/py_replay.mcap
replay: replay_py_watch life 1: first divergence at release 50:
  output replay/py_tally byte 0: recorded 32 00 00 00 00 00 00 00 ..., replayed 33 00 00 00 00 00 00 00 ...
replay: 223 of 496 compared releases differ
facts: ...
replay: running release 496, the life's last; its output is in no record

Up to 16 bytes are shown: the first eight are the tally's release, 50 recorded and 51 replayed, and ... stands for the eight after them. Exit 1. What the replay recomputes with the script you run are each input's age and staleness and the body, so an edited body or a changed stale_after is a what-if. An input or output of another payload, order or count, a period or policy, or a parameter of another name, kind or order is refused, naming both declarations; a changed default or range replays.

The end of a replay

The verdict comes before the last release runs, and the process ends inside run():

 wait for record 0 ... wait for record 496:  the verdict, the facts, the last-release line
                                             on standard output
 body of release 496                         runs uncompared: its output is in no record
 the next wait                               ends the process: exit 0 identical, 1 not

run() neither returns nor raises at the end of a replay: a caught exception could not stop the loop from running a release no record holds. The end is a process exit, so it skips what a process exit skips: atexit callbacks, finally and with around run(), finalizers, non-daemon threads, and files the node buffered itself.

What the body prints is not lost. run() flushes sys.stdout and sys.stderr before it opens the node and before every release, live and in a replay. replay_py_watch.py print prints release K from every body; read through a pipe, its replay shows:

release 0

release 495
replay: replay_py_watch life 1: 497 releases, 496 compared, identical
facts: ...

The script, in a replay Exit Says

replay_py_watch.py early calls sys.exit(0) in release 60's body, and its replay ends with the "ended before release 61" line and exit 1. Only the identical line on standard output is a pass: a script that leaves through os._exit(0) has passed nothing.

def variant_of(argv):

    if len(argv) < 2 or argv[1] == "--replay":
        return None

Payloads

Import a standard payload from tail_messages: Vector3, Point, Quaternion, Pose, Twist, Range, Imu, Odometry, and Range's named values RANGE_ULTRASOUND and RANGE_INFRARED. The module is printed by the image build from the Rust crate robot_messages, field for field, with the unit of each field in a comment, and it checks itself when imported: each declaration asserts that its size, alignment and layout identity are the Rust struct's, so a module edited by hand stops at AssertionError: Range.

The geometry conventions are in the module, in each record's comment, the words the Rust records carry: right-handed axes, x forward, y left and z up in a body frame; a positive angle turns counter-clockwise about its axis, so a yaw of +15 degrees turns left; Quaternion is a Hamilton quaternion stored x, y, z, w, with w the scalar, the identity (0, 0, 0, 1) and all zero meaning "not estimated"; a Pose used as a transform is the pose of the child frame in the parent frame; a Range reading lies on the sensor frame's +x axis; Odometry's pose is base_link in odom. The arithmetic on them (composition, inversion, a rotation from roll, pitch and yaw) and frame sets with their lookup are Rust only in this release (Frames and transforms); they will reach Python as bindings that call the Rust code, never as a pure-Python copy. Until then a Python node computes them by hand, against these conventions.

Declare a payload of your own when no standard one fits. A payload crosses shared memory to a peer that may be written in Rust, so its layout is that of a Rust #[repr(C)] struct. Declare the fields and the framework computes it:

Gate = Payload("stamp_ns:u64 state:u32=OPEN:0|CLOSED:1 reserved:u32", "Gate")
Gate.size       # 16 -- the same as the Rust struct
Gate.align      # 8
Gate.canonical  # "{stamp_ns:u64,state:u32=OPEN:0|CLOSED:1,reserved:u32}"
Gate.layout     # 0xa39598f2 -- the identity of that text, the one the Rust derive computes
Declaration Rust
u8 i8 u16 i16 u32 i32 u64 i64 the same
f32 f64 the same
name:u8[32] [u8; 32] — arrives as bytes
name:u32[4] [u32; 4] — arrives as a tuple
name:Vector3, with using=(Vector3,) a field of a nested record — read as name.x
name:u32=OPEN:0|CLOSED:1 a field with named values, #[wire_plain(values(OPEN = 0, CLOSED = 1))]

A declaration a Rust payload could not have is refused at the declaration, with what to do:

Declaration NodeError
"stamp:u64 counter:u32" payload 'Refused' has padding at its end; name it with a reserved field
"flag:u8 count:u64" payload 'Refused' has padding before 'count'; reorder the fields or name the gap with a reserved field
"pressed:bool .." payload 'Refused': 'pressed' is a bool, which cannot cross the wire: only 0 and 1 are valid and a sender may send 2. Use u8.
"from:u32 to:u32" payload 'Refused': 'from' is not a usable field name; a field is declared in C, C++ and Python alike, ..
"align:u64[0]" payload 'Refused': 'align' is an array of no elements
"gain:f32=UNITY:1 .." payload 'Refused': only an integer field has named values

An array of arrays or of payloads has no declaration here.

Payload.instance(**fields) makes a value to publish. Every field must be given; a nested field is given an instance of its payload.

Why not a struct format string. struct pads with native alignment only under @; under <, >, = and ! it packs tight. So repr(C) { u32, u64 } is 16 bytes while struct.calcsize("<IQ") is 12, and a wrong prefix would give you a subscriber reading a shifted field. There is no prefix to get wrong here. (ctypes is not available on TailOS: there is no libffi.)

What is checked, and what is not. The payload's size and its layout identity -- a 32-bit FNV-1a over the canonical text, computed from field names, their order, their types, nesting, array lengths and named values -- are checked against the other end at open, on every lane: a node whose payload disagrees does not start, and run() raises an OSError naming the topic. On kernel the reason also says what the topic carries, and the console record ends with it:

could not start: topic `range/front` refused the open: this is not the payload type the topic carries: it carries 32-byte payloads of layout 0x6772d100

A kernel topic lives while an end holds it, so a corrected declaration is not refused for ever: once every end of the old payload has closed, the corrected one creates the topic anew. So two declarations with the same fields in another order are refused, in any language pair. Not compared: the payload's name (Point read as Vector3 is admitted: the bytes are the same three f64), a field's unit, and the lane.

Cycle

Everything about one input at this activation. A node has one per input, passed to its body in the order the inputs are declared.
get() The sample, or None if absent or stale
copied() The same sample, in an object of its own
arrived() Whether a newer publication was taken at this release
since_received() Seconds since a sample last arrived at this node, or None if none ever has. Exactly zero on the release arrived() is true
was_stale() Whether something was received and is now older than this input's stale_after
missed() Publications the lane lost for this input since the previous cycle. Not a running total
rejected() Publications the transport refused since the previous cycle
overruns() Releases the node missed since its previous cycle ran
is_healthy() No loss, no rejection, no overrun
topic() The name of the topic this input reads, whatever the parameter is called

An input is in one of three states on every release:

get() was_stale() since_received()
a sample False a number usable: received, and within stale_after
None False None not yet: nothing has been received
None True a number stale: what was last received is older than stale_after

"Not yet" has no deadline. An input that has never received anything is absent and is not stale, however long that lasts: there is no receipt to measure an age from. A node that must act when a publisher never comes up tests get() is None, which is true for "not yet" and for stale alike, and not was_stale(). On QEMU a node's input on a topic nobody publishes read "not yet" on every one of about 520 releases.

get() answers "is there a usable reading"; arrived() answers "is it a new one". A node fed by a slower input sees a usable reading every cycle and a new one on some. examples/estimator.py applies its odometry correction once, on the release it arrives:

class Estimator:
    """A dead-reckoned heading, corrected by the wheels whenever they report."""

    def __init__(self):
        self.pose = Pose.instance(x_mm=0, heading_mrad=0, corrections=0)

    def step(self,
             imu=subscribe(IMU_DATA, stale_after="35ms"),
             odometry=subscribe(WHEEL_ODOMETRY, stale_after="65ms"),
             estimate=publish(ESTIMATE_POSE)):
        """Predict from the IMU, correct from the wheels when they report, publish the pose."""
        rates = imu.get()
        if rates is None:
            return                                # no usable IMU: publish nothing this cycle
        self.pose.heading_mrad += rates.yaw_rate_mrad_s // 100
        wheels = odometry.get()
        if odometry.arrived() and wheels is not None:
            self.pose.x_mm = wheels.travelled_mm  # once, on the cycle the reading arrives
            self.pose.heading_mrad = wheels.heading_mrad
            self.pose.corrections += 1
        estimate.publish(self.pose)


periodic(every="10ms", on_overrun=Skip)(Estimator().step)
run()

This file is run on the host only, against a stand-in for the transport; no on-target test runs it.

An input is a value, the newest one. A node behind a faster publisher is handed the newest publication at each release. The ones a newer one replaced are handed to nobody and are not missed(). So a topic that carries increments must not be read as an input: the odometry above is a cumulative reading for that reason. What missed() counts is the lane's own: on the kernel lane, the publications the topic overwrote before the node read them, counted from the input's open (the topic keeps its newest 8, and up to 20); on the other two, the ones the lane itself reports skipped. rejected() is always 0 on the kernel lane: a publisher of another payload is refused when it opens.

overruns() is the node's, not an input's. Every input's cycle of one release carries the same number. Read it from one of them: adding them up counts each overrun once per input. A node with no input has no Cycle to read it from, and an overrun is not written to the system log on this surface: under Skip or CatchUp a Python node that only publishes cannot observe its overruns at all.

get() borrows. It returns the same object every cycle with its fields rewritten, which mirrors Rust's get() -> Option<&T>. A body that keeps it and reads it next cycle sees new data — use copied() to keep one. Rust's borrow checker catches that mistake; Python's cannot, so it is stated here instead. The Cycle objects themselves are the same ones on every release too.

That reuse is not an optimisation detail you can ignore: it is what keeps a cycle free of allocation the garbage collector has to walk. See Cost.

run()

run()

Runs the declared node, and does not return until its policy stops it. When the command line ends in --replay FILE [--life N] it replays the node instead, and never returns: the process ends inside it, after the last release or at a refused replay (Recording and replay).

It hands the framework the whole of sys.argv as it is when run() is called, each entry as its file-system bytes, and the framework reads only that trailing part: a script that consumes its own arguments by rewriting sys.argv before run() hands over what is left. It flushes sys.stdout and sys.stderr before it opens the node and before every release, skipping one that is None, so what a body printed is written before any call that may end the process.

Decoration cannot do this itself: a module whose import never finishes is never entered into sys.modules, and every traceback from it is reported inside an import. rclpy.spin exists for the same reason.

A process is one node — which is what the Rust attribute enforces by generating main. Declaring two raises, naming both.

The node starts at its first release, not when run() opens its topics. Whatever was published before that is thrown away unread: when it was received is not known, and it must not be presented as fresh. The time run() spends between opening the topics and the first release, freezing the heap among it, is not charged to the node as overruns. Limit: an input reads "not yet" on the first release unless another program published in the instant between that discard and the release's own read.

run() opens the topics the node publishes first, in the order they are declared, then its inputs in the order the parameters are written. The node waits for a topic nobody publishes yet for ten seconds in all: one wait for the node, not one per topic. A kernel-lane input never waits: it is admitted with no publisher and reads "not yet" until one publishes. While the node waits for a later input it holds nothing, and what was published meanwhile is dropped at the first release.

Safety

A Python node cannot declare a topic safety-relevant, and this is deliberate.

A safety classification asserts that a bound on cycle time exists and is known. Measured on target, under QEMU:
A full collection, against a bare interpreter heap 6.6 ms worst, 4.4 ms median
An incidental collection inside a 20 ms release grid 2.5 ms — 12.7% of the period

Both the pause and its frequency scale with your live heap, which this framework neither observes nor bounds. There is no bound to assert, so the claim is not available to make.

A Python node is Quality Managed by construction, in the way the fast lane is by its own design. It may subscribe to a topic another node has classified safety-relevant — consuming safety-relevant data at QM is an ordinary architecture. What it may not do is claim the classification for what it publishes. Put that node in Rust.

Cost

Measured on target under QEMU on 2026-09-09, on a node with one input. These are not board numbers — QEMU's CPU is not a Raspberry Pi 3's. The ratios should hold; the absolute milliseconds should not be quoted. They were not measured again for a node with several inputs.
Smallest period with no overruns 5 ms (1 ms overran 35 cycles in 200)
Lateness against the grid median ~0.9–1.0 ms, p99 ~1.7 ms, at every period
Time to the first release cold ~4.2 s, warm ~1.4–1.9 s

That last row matters to a system integrator: a Python node is not ready for seconds after it is spawned. It is interpreter startup, not this framework, and the framework's admission wait already spans it, which is why a Python subscriber may still be started before its Rust publisher.

What the framework does about the collector, so you do not have to:

  • run() calls gc.freeze() before the first release, moving the interpreter's whole startup heap out of the generations the collector walks. Measured: a full collection costs 6.6 ms before that call and 0.018 ms after it.
  • Nothing the collector walks is allocated per cycle, whatever the number of inputs. The cycle objects, the sample each get() returns and the payload buffers are created once. On QEMU, a node with three inputs grew the collector's tracked objects by 0 and the interpreter's allocated blocks by 0 between its releases 300 and 500, in each of six runs; the test allows fewer than 20 blocks.
  • A node's run-time parameters are handed in one argument tuple, built at the first release and rebuilt only on a release whose values differ from the previous release's: that release makes the new tuple and the new values' objects, and every other release makes nothing for them. The first release's tuple is built after gc.freeze(), so it is the one object the collector walks that a node without parameters does not have. Measured on the host, not on target: a node with three parameters kept nothing over 400 releases without a set.

What you can do. A body that does not retain what it makes triggers no collection at all — CPython collects on allocations minus deallocations. Keeping a rolling window of samples is what makes the collector run; if you need one, that is the cost to measure.

Errors

A missing or unknown key, a topic without its lane, a body the loop cannot call NodeError at decoration, naming it

A declaration in the earlier grammar, publish= among its keys NodeError at decoration, once, with its rewrite

A declaration with padding, a bool, an empty array, a keyword for a name, or named values on a float NodeError at the declaration, naming the field

active.feedback, succeed or abort from a thread the body started RuntimeError, on every such call: the node is reached only from the thread that called run() (Actions)
A body's feedback, succeed or abort with no goal running at its release NodeError from the call

A refused replay: a malformed --replay ... tail, a file that is not a recording of this node, another declaration, no such life no exception: one line on standard error and the process ends inside run(), exit 2 for the tail and 1 for the rest, before any topic is opened (Recording and replay)

A node that cannot start names the topic. This node, from the project's tests, declares two inputs, the second on a topic nobody creates, and catches what run() raises:

try:
    run()
except OSError as reason:
    print(f"[never_appears] {reason}")
    if reason.filename != MISSING.name:
        sys.exit(5)
    if reason.errno != NEVER_APPEARED:
        sys.exit(3)
    sys.exit(0)

On QEMU it printed, about eleven seconds after the interpreter was started:

[never_appears] [Errno -3] the topic never appeared: 'py_two_inputs/nobody'

Before the exception is raised, the layer beneath writes what was wrong on the console, one line per fact. This node publishes a topic, which it had created before it waited; a node with several outputs gets one such line per output it had created, in declaration order:

could not start: topic `py_two_inputs/nobody` never appeared
its publication `py_two_inputs/orphan` is left without a writer

Limits: those records are on the console only, not in the system log, and they name no node. Only the first topic that could not be opened is named. The topic the node had created stays owned by the process until it exits.

After Fault stops a node, a Cycle the body kept reads as nothing. The fixture fault_node.py in the same directory keeps the cycle it is handed, overruns once on purpose, and asks the kept cycle afterwards:

try:
    run()
except NodeError as stopped:
    print(f"[fault] {stopped}")
    if not usable_on_the_last_release:
        sys.exit(7)         # nothing was usable to lose, so the check below would prove nothing
    cycle = kept[0]
    if cycle.get() is not None or cycle.arrived() or cycle.since_received() is not None:
        print("[fault] a cycle kept from the last good release still reads as usable")
        sys.exit(8)
    sys.exit(0)

[fault] node: a cycle overran its deadline, and this node declared on_overrun=Fault

init has no equivalent, and does not need one

Rust needs init because a bare fn cannot own state between calls. A Python closure, a module global or a bound method already does. publisher.py above keeps its counter in a module global. estimator.py keeps its pose on an object and declares the method bound to it:

periodic(every="10ms", on_overrun=Skip)(Estimator().step)

A method decorated inside its class body is refused: its first parameter is self, which no topic feeds. The message gives the bound form above.
