The Periodic Framework

A robotics application is a set of things that happen on a cadence: read a sensor every 20 ms, run a controller every 5 ms, publish a state estimate every 100 ms. The periodic framework owns that cadence, so an application declares what it is and writes only the work.

This is the periodic half of the TAIL OS application framework. The aperiodic half is the service framework: one dispatch per external event, rather than one per elapsed period.

A complete node

This is an entire program. There is no main — the attribute generates it.

#![feature(tail_core)]

use periodic::periodic;

/// A sensor reading. `repr(C)` and `Copy` because it crosses shared memory.
#[derive(Clone, Copy)]
#[repr(C)]
struct Range {
    stamp: u64,
    range_mm: u32,
    quality: u32,
}

// SAFETY: `repr(C)`, all-integer, every bit pattern valid.
unsafe impl std::tail_core::sync::shared_mutex::ShmSafe for Range {}

#[periodic(every = "20ms", publish = "sensor/range", lane = safe, on_overrun = Skip)]
fn lidar() -> Range {
    Range { stamp: 0x1234_5678, range_mm: 4200, quality: 97 }
}

The framework opens the topic — retrying, so startup order is not the application's problem — releases the body at start + n * period, publishes the return value, and counts every release the body ran past.

Add the crate as a direct dependency:

[dependencies]
periodic = { path = "<relative path to>/framework/periodic/lib" }

periodic is a standalone direct dependency, not re-exported through tail_core, so adding it forces no toolchain or std rebuild.

Node shapes

A node's shape follows from which topic keys it declares. The macro checks the parameter list against the declaration, so a mismatch names the missing half rather than surfacing as a trait-bound error against generated code.

Declares Body signature Meaning
publish fn f() -> T Produces a sample every cycle
subscribe fn f(input: Cycle<T>) Consumes a sample every cycle
both fn f(input: Cycle<In>) -> Out Transforms: reads, computes, publishes
plus init state comes first: fn f(state: &mut S, input: Cycle<T>) Keeps something between cycles

A node that declares neither publish nor subscribe is refused: it is a timer, and the framework has nothing to offer it.

The periodic attribute

#[periodic(every = "20ms", subscribe = "sensor/range", lane = safe,
           stale_after = "60ms", on_overrun = Skip)]
Key Value Required
every duration — the release period yes
lane kernel, safe, or fast yes
on_overrun Skip, CatchUp, or Fault yes
publish topic name to publish on one of publish/subscribe
subscribe topic name to read from one of publish/subscribe
stale_after duration after which a sample reads as absent yes, if subscribe
init expression building the node's state no
safety bare flag: this topic carries safety-relevant data no

Three rules are enforced at build time:

  • on_overrun has no default. A cycle that misses its deadline is a safety-relevant event, and a policy acquired by silence is emergent behaviour. Omitting it does not compile.
  • subscribe requires stale_after. Without it there is no answer to "is this data still usable", and the node would act on whatever it was last given.
  • A safety topic cannot bind to a QM-only lane. This is a const assertion in the generated main, so it fails the build rather than a review.

String-valued keys are expressions, not just literals, so a node can keep its period and topic names in named constants — which is what lets a test assert on them:

const PERIOD: &str = "20ms";
const TOPIC: &str = "sensor/range";

#[periodic(every = PERIOD, publish = TOPIC, lane = safe, on_overrun = Skip)]
fn lidar() -> Range { read_sensor() }

Durations

An integer followed by a unit. Parsed at startup; a typo is reported naming the literal rather than silently defaulting to something plausible.

Unit Meaning
ns nanoseconds
us microseconds
ms milliseconds
s seconds

"20ms", "1s", "500us", "250ns". There is no fractional form — write "1500us", not "1.5ms".

Publishing, and declining to publish

A publishing node's return type decides whether it may skip a cycle. No attribute key selects between them; the compiler picks from the return type.

// Always publishes.
#[periodic(every = "20ms", publish = "sensor/range", lane = safe, on_overrun = Skip)]
fn lidar() -> Range {
    read_sensor()
}

// Publishes only when it has something to say.
#[periodic(every = "20ms", publish = "sensor/range", lane = safe, on_overrun = Skip)]
fn lidar() -> Option<Range> {
    read_sensor_if_ready()
}

Prefer T when the node always produces a sample. Option<T> costs a copy that T does not: a node that may decline has to decide before entering the fill path, which forces the value onto the stack first.

Returning None is not an overrun and is not counted as one. "I had nothing to say" and "I did not finish in time" are different facts, reported through different fields.

State that outlives a cycle

A node that must keep something between cycles — a device handle, a filter, an accumulator — names how to build it with init and takes it as its first parameter, by &mut.

use periodic::periodic;

#[derive(Default)]
struct Cycles(u64);

#[periodic(every = "20ms", publish = "diag/counted", lane = safe, on_overrun = Skip,
           init = Cycles::default())]
fn counter(cycles: &mut Cycles) -> Count {
    cycles.0 += 1;
    Count { cycles: cycles.0 }
}

The state is built once, before the first release, and the same one is handed back on every cycle. It is dropped when the node stops.

An actuator holding a device handle is the ordinary shape, not an exception. Without init such a node would reach for a static, which is the boilerplate the framework exists to remove.

With both init and subscribe, state comes first:

#[periodic(every = "5ms", subscribe = "input/pad", lane = kernel, stale_after = "300ms",
           on_overrun = Skip, init = Motor::attach())]
fn drive(motor: &mut Motor, pad: Cycle<Command>) {
    motor.set(pad.get().map_or(Command::Stop, |command| *command));
}

Cycle: one activation's inputs

Everything a node needs to know about this cycle arrives on one value. None of it is a counter the node must remember to poll.

Method Returns Meaning
get() Option<&T> The sample, if present and fresher than stale_after
copied() Option<T> The same, copied out, for a node that would rather own it
since_received() Option<Duration> How long since this node last received a sample
was_stale() bool Data was held, but older than stale_after
missed() u32 Publications lost since the previous cycle — not cumulative
rejected() u32 Publications the transport refused — not cumulative
overruns() u32 Releases missed since the previous cycle ran
is_healthy() bool No loss, no rejection, no overrun

Staleness collapses into absence

get() returns None both when nothing has ever arrived and when what arrived is older than stale_after. That is deliberate: the fail-safe branch becomes the default branch, and a node takes it without having to know that staleness is a concept.

#[periodic(every = "20ms", subscribe = "sensor/range", lane = safe,
           stale_after = "60ms", on_overrun = Skip)]
fn brake(lidar: Cycle<Range>) {
    match lidar.get() {
        Some(reading) => brake_for(reading.range_mm),
        None          => brake_for(0),   // absent OR stale — one case
    }
}

A transport's own read() cannot draw this distinction: it returns None for an empty topic, which does not separate "nothing published yet" from "the publisher died three seconds ago". was_stale() is there for the node that genuinely needs the difference — but nothing requires a node to ask, which is the property that matters.

What since_received does and does not measure

It is the interval since a sample last arrived at this node, taken from the same monotonic counter the cadence runs on. It is not the sample's publication age: no transport timestamps a publication.

It does not include the time a sample spent between publication and this node's next read. That is bounded by the node's own period, but it is not measured.

Counters are per-cycle

missed(), rejected() and overruns() report what happened since the previous cycle, not a running total. A node that wants per-cycle loss from a transport counter would have to store-previous-and-subtract itself — and one that forgets never sees loss at all, because the total climbs silently for the life of the process. The subtraction happens once, here.

Overruns are delivered once and then cleared, following the same read-and-clear shape as POSIX timer_getoverrun.

Cycle borrows its sample rather than owning it, and is deliberately not Send: subscribing and reading a topic must happen on the same thread, so this is a compile error rather than a node that silently never receives anything.

Overrun policies

What a node does when a cycle does not finish before its next release. The three differ in what they preserve.

Policy Preserves Use when
Skip Phase — output stays on the start + n * period grid, with gaps rather than drift A control loop, where a command computed from stale inputs and delivered late is worse than no command
CatchUp Count — every release eventually runs, back to back until caught up An integrator or accumulator that must see every interval exactly once
Fault Neither — the node stops and reports The deadline is the safety requirement, and continuing on any terms is the wrong answer

Skip is the right default for control. CatchUp does not preserve phase while catching up, but is bounded by construction: one overrun schedules at most the releases it actually passed, so a persistently slow node degrades to running continuously rather than accumulating unbounded backlog.

Under Fault the node exits with NodeError::DeadlineMissed rather than returning success, so a supervisor can tell a missed deadline from a clean shutdown.

Lanes and safety classification

One trait spans all three transports, so the executor is written once and changing lane changes no application code beyond the declaration.

lane = Cost Safety class
kernel One copy into a kernel pool cell, one kernel call per message Safety
safe Four kernel calls per message, zero-copy, with prevention Safety
fast Zero kernel calls, no lock, zero-copy QM only

fast is Quality Managed only by its own design: its writer holds a standing read-write mapping of every slot for the region's lifetime, so it can alter a frame a reader is parsing. That is detection, not prevention.

So this does not compile:

#[periodic(every = "20ms", publish = "brake/command", lane = fast,
           on_overrun = Skip, safety)]
fn brake_command() -> Command { ... }
//  error: a safety-classified topic cannot be carried on a QM-only lane

A single API spanning a safety lane and a QM-only lane means the declaration carries the classification — and a framework that could not enforce that would have made the dangerous choice exactly as easy as the safe one.

Known gap. The lane a topic is carried on is not currently compared between publisher and subscriber. Two processes that disagree about the lane fail as a subscriber that silently never receives anything, rather than with a diagnostic.

There is deliberately no maximum-payload constant on the lane trait. Every transport already refuses an over-large shape at open, before any syscall; predicting that refusal would only add a second place to be wrong.

Payload requirements

A payload crosses shared memory, so every bit pattern must be valid and it must be Copy.

#[derive(Clone, Copy)]
#[repr(C)]
struct Range {
    stamp: u64,
    range_mm: u32,
    quality: u32,
}

// SAFETY: `repr(C)`, all-integer, every bit pattern valid.
unsafe impl std::tail_core::sync::shared_mutex::ShmSafe for Range {}

The publisher's and subscriber's types must match exactly; a mismatch is refused by the shape check at open.

Startup failures

A node that cannot reach its topic says which and why, then exits non-zero. It does not run forever reading None, which is the failure mode that looks like a working node with a quiet peer.

NodeError Cause
BadDuration(text) A duration literal could not be parsed
UnusablePeriod The period is zero, or rounds to zero ticks on this clock
NeverAppeared(topic) A topic did not appear within the admission attempts
Refused(topic, error) The transport refused the open for a reason retrying will not fix
DeadlineMissed(node) A cycle overran under on_overrun = Fault

Admission retries because the kernel deliberately refuses a name nobody publishes yet — so a misspelled topic fails loudly at startup instead of becoming a topic that never delivers. The retry has to exist somewhere, and one bound with one diagnostic beats one per application.

The executor, directly

Most applications never touch this: the attribute drives it. It is public because the cadence is testable without a topic, and a node with an unusual shape may want it.

use periodic::{Executor, OverrunPolicy};
use core::time::Duration;

let mut executor = Executor::new(clock, Duration::from_millis(20), OverrunPolicy::Skip)?;
executor.run(|overruns| {
    // one cycle; `overruns` is per-cycle, already cleared
});
Item Purpose
Executor::new(clock, period, policy) Start releasing every period, from now
Executor::step(body) Run one cycle; returns false when the policy has stopped the node
Executor::run(body) Run until the policy stops the node
Executor::release() / period() The next release, and the period, in clock ticks
Clock now(), ticks_per_second(), sleep_until(deadline)
next_release(policy, release, period, now) Pure function: releases missed, and where the next one falls
period_ticks(period, ticks_per_second) A declared period in ticks, or None if unrepresentable

Releases are placed at start + n * period and slept to, never "now + period" slept for. The difference is not stylistic: sleep reads the clock inside the kernel, after the trap, so a relative loop adds every cycle's scheduling delay to the period and never recovers it.

next_release is a free function over ticks rather than a method on a clock, so every overrun case is exhaustively testable without a clock at all.
