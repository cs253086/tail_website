Periodic Framework — Rust API

Declare a period and the topics; the framework owns the timing loop, topic admission, freshness and the publish. A node is a function with an attribute — there is no main to write.

A periodic node is what you would otherwise create by hand as a thread running a timer loop — spawn a task, read the clock, do the work, sleep for the remainder, repeat. The framework replaces that loop, so you never write the thread, the sleep, or the drift correction the hand-written version needs.

A node reads any number of topics, each declared on the parameter that receives it and each with its own freshness bound, and publishes any number, each declared on the parameter that hands the body its output.

This page is the Rust API; the Python page describes Python's.

Quick start

One file, one node. counter runs every 100 ms, keeps a count of its releases, and publishes it:

// app/counter/src/main.rs

use periodic::{periodic, KernelLane, Out, Topic};
use wire_plain::WirePlain;

/// What the counter publishes on every release.
#[derive(Clone, Copy, Debug, WirePlain)]
#[repr(C)]
pub struct Releases {
    /// Releases run so far, this one included.
    pub count: u64,
    /// When this release ran [ns since boot].
    pub stamp_ns: u64,
}

/// The counter's releases, published by the counter alone.
const COUNTER_RELEASES: Topic<Releases, KernelLane> = Topic::new("counter/releases");

#[periodic(every = "100ms", on_overrun = Skip, init = 0u64)]
fn counter(count: &mut u64, #[publish(COUNTER_RELEASES)] releases: Out<Releases>) {
    *count += 1;
    releases.publish(Releases { count: *count, stamp_ns: periodic::now() });
}

init = 0u64 builds the node's state once, before its first release, and the body is handed it by reference on every release after: the one parameter with no marker. The other parameter is the node's output: whatever the body hands releases.publish(..) is published on counter/releases when the body returns. Releases is a payload of this program's own; #[derive(WirePlain)] proves it can cross to another process unchanged.

Build, run and check it

With the Raspberry Pi 3 board support package (BSP), save the file as app/counter/src/main.rs, add /usr/bin/counter=counter to the [disk] section of the BSP's tail.build, and run ./make-disk.sh. It builds the program against the SDK and puts it in /usr/bin on the image (Installing TAIL OS on Raspberry Pi 3). There is no Cargo.toml to write and no main: the attribute writes it.

On the booted image, start it in the background and look at it:

tsh> counter &
tsh> node list
counter  pid 5  counter
tsh> topic echo -n 3 --as "count:u64 stamp_ns:u64" counter/releases
# counter/releases: kernel lane, --as, 16 B, layout 0x79e81151
count=1 stamp_ns=161062928
count=2 stamp_ns=260987952
count=3 stamp_ns=360967504

node list shows every running node: its name, its process and its program; the pid and the counts on your system differ. topic echo reads the node's topic as any other program would; --as tells it the payload's fields, since Releases is not one of the standard payloads it decodes on its own. Each count is one more release. The shell tools page describes both tools.

Your first nodes

Four files in the BSP's app/ directory: the topics, defined once, and three programs that each have an end of one. No program writes a main, a thread, a sleep or a retry loop.

File Is
app/robot_topics.rs the topics: each one's name, payload and lane
app/lidar/src/main.rs a node that publishes sensor/range
app/brake/src/main.rs a node that reads sensor/range
app/drive/src/main.rs a node that reads sensor/range and cmd/velocity

lidar publishes sensor/range, which brake and drive read; drive also reads cmd/velocity from a pad or planner not written here.

The topics, defined once

// app/robot_topics.rs

// Each program uses some of these definitions and not others.
#![allow(dead_code)]

use periodic::{KernelLane, SafeLane, Topic};
pub use robot_messages::{geometry::Twist, sensor::Range};

/// The front range sensor's readings, in the `range_front` frame: one writer, so the safe
/// lane.
pub const SENSOR_RANGE: Topic<Range, SafeLane> = Topic::new("sensor/range");

/// Velocity commands, in the `base_link` frame: a pad and a planner both write them, so
/// the kernel lane.
pub const CMD_VELOCITY: Topic<Twist, KernelLane> = Topic::new("cmd/velocity");

A topic definition is three facts in one constant: the name, the payload it carries and the lane that carries it. Every end of the topic is opened from that constant, so no program states any of the three a second time, and two programs that import one definition cannot disagree about them. The frame a payload's numbers are in belongs to the topic, and its doc comment names it.

Range and Twist are standard payloads, from the crate robot_messages: one definition of each, which Python's tail_messages is generated from, so a Python node at the other end holds the same one. A payload of your own is a struct with #[derive(WirePlain)]; see Payloads. No program here writes unsafe.

A publisher

Reads a sensor every 20 ms and publishes the reading, stamped with the time it was taken. This is the whole program:

// app/lidar/src/main.rs

#[path = "../../robot_topics.rs"]
mod robot_topics;

use periodic::{periodic, Out};
use robot_topics::{Range, SENSOR_RANGE};

#[periodic(every = "20ms", on_overrun = Skip)]
fn lidar(#[publish(SENSOR_RANGE)] range: Out<Range>) {
    range.publish(Range {
        stamp_ns: periodic::monotonic_ns(),
        radiation_type: Range::INFRARED,
        field_of_view: 0.05,
        min_range: 0.02,
        max_range: 8.0,
        range: 4.2,
        variance: 0.0,
    });
}

periodic::monotonic_ns() is the stamp clock: nanoseconds since boot on the counter the node's releases are placed on. Range::INFRARED is one of the payload's named values.

The lidar stamps with monotonic_ns() because it is at the hardware boundary: the stamp is the instant it read the device. A node that decides something from its inputs stamps with periodic::now() instead -- the current release's one clock reading, in nanoseconds, the instant every input of the release was judged against; 0 before the first release -- or copies an input's stamp_ns. A replay of the node (below, "Recording and replay") hands the body the recorded now(), so what it stamps replays exactly; monotonic_ns() reads the counter as the body runs, which no recording holds.

A subscriber

Reads that topic every 20 ms and brakes on it. stale_after says how old a reading may be before it counts as absent, so the fail-safe branch is the one that runs when the sensor goes quiet:

// app/brake/src/main.rs

#[path = "../../robot_topics.rs"]
mod robot_topics;

use periodic::{periodic, Cycle};
use robot_topics::{Range, SENSOR_RANGE};

#[periodic(every = "20ms", on_overrun = Skip)]
fn brake(#[subscribe(SENSOR_RANGE, stale_after = "70ms")] lidar: Cycle<Range>) {
    match lidar.get() {
        Some(reading) => brake_for(reading.range),
        None => brake_for(0.0), // absent or stale
    }
}

// Your actuator call goes here: brake for an obstacle `range` metres away, 0 meaning now.
fn brake_for(_range: f32) {}

A node with two inputs

The obstacle-stop drive node: a velocity command on the kernel lane and a range reading on the safe lane, each with its own bound, and a device handle kept between cycles.

// app/drive/src/main.rs

#[path = "../../robot_topics.rs"]
mod robot_topics;

use periodic::{periodic, Cycle};
use robot_topics::{Range, Twist, CMD_VELOCITY, SENSOR_RANGE};

/// The range inside which whatever is ahead is an obstacle [m].
const STOP_WITHIN: f32 = 0.3;

/// The motor driver, and the speed it was last given.
struct Motors {
    speed: f64,
}

impl Motors {
    /// The motors, at rest. Claim the device here.
    fn attach() -> Self {
        Motors { speed: 0.0 }
    }

    /// Drive at the commanded forward speed [m/s].
    fn drive(&mut self, twist: &Twist) {
        self.speed = twist.linear.x;
    }

    /// Stop, if moving.
    fn stop(&mut self) {
        if self.speed != 0.0 {
            self.speed = 0.0;
        }
    }
}

#[periodic(every = "20ms", on_overrun = Skip, safety, init = Motors::attach())]
fn drive(
    motors: &mut Motors,
    #[subscribe(CMD_VELOCITY, stale_after = "310ms")] command: Cycle<Twist>,
    #[subscribe(SENSOR_RANGE, stale_after = "70ms")] range: Cycle<Range>,
) {
    match (command.get(), range.get()) {
        (Some(twist), Some(range)) if range.range > STOP_WITHIN => motors.drive(twist),
        _ => motors.stop(), // no usable command, no usable range, or an obstacle
    }
}

A command may be 310 ms old and still be acted on; a range reading only 70 ms. One match arm covers every way either input can be missing.

Build and run

Each program is built with the Raspberry Pi 3 board support package (BSP). Add /usr/bin/lidar=lidar, and the same line for brake and drive, to the [disk] section of the BSP's tail.build; ./make-disk.sh builds each app/<name>/src/main.rs against the SDK's periodic crate and puts it in /usr/bin on the image. There is no Cargo.toml to write. See Installing TAIL OS on Raspberry Pi 3. A program's name is at most 32 bytes: a longer one is left out of the image's program table, so it never starts and leaves no record.

On the booted image start them in the background, in any order: lidar &, brake &, drive &. No program names another. The framework opens each topic and waits for its publisher (see Start-up). Nothing here publishes cmd/velocity, so drive runs and stays stopped: that input is absent, and absent is the _ arm.

periodic, wire_plain and robot_messages are libraries of the SDK, so a program names each with a use and nothing more. Two lines are there only because the BSP's one-file programs share a file:

Line Why
#[path = "../../robot_topics.rs"] mod robot_topics; compiles the one definitions file into this program
#![allow(dead_code)], in the definitions file a program that leaves a definition unused would otherwise be warned about it

In a cargo workspace the definitions are a library crate instead. robot_topics/src/lib.rs then needs no #![allow(dead_code)]; each program lists periodic and robot_topics in its Cargo.toml and starts at its use lines. A payload that a Python program must also read lives in a crate of its own that depends on wire_plain alone: the host generator that prints its Python definitions imports it, and cannot import a crate that depends on periodic. The rest of this page shows a program from its use lines on.

#[periodic] keys

The header says what is true of the node. A topic the node reads is declared on the parameter that receives it, and a topic it publishes on the parameter that publishes it.

Where Key Required
header every = "<duration>" always
header on_overrun = Skip | CatchUp | Fault always
header init = <expr> exactly when the body takes a state
header safety no
parameter #[subscribe(TOPIC, stale_after = "<duration>")] once per input
parameter #[publish(TOPIC)] once per output

every — required

#[periodic(every = "20ms", on_overrun = Skip)]

The release period. Releases fall on start + n * period, never drifting. A duration.

on_overrun — required

#[periodic(every = "20ms", on_overrun = Skip)]

What to do when a cycle runs past its next release: Skip, CatchUp, or Fault, written as the bare word. No default — omitting it does not compile. See OverrunPolicy.

#[publish(TOPIC)] — on a parameter

use periodic::{periodic, Out};
use robot_topics::{Range, SENSOR_RANGE};

#[periodic(every = "20ms", on_overrun = Skip)]
fn lidar(#[publish(SENSOR_RANGE)] range: Out<Range>) {
    range.publish(Range { stamp_ns: periodic::monotonic_ns(), range: 4.2, ..Range::default() });
}

One output: the topic the body publishes on. The parameter's type is Out<T> of the topic's payload, periodic::Out<'_, T> with its lifetime left out. The body hands it a whole value with publish, which takes the handle, so an output publishes at most once a release. Nothing is sent at the call: every value handed to an output is published when the body ends, in the order the outputs are declared, and nothing at all is published for a body that panics. A node has as many outputs as it has such parameters, each on its own topic. An output the body does not publish on a release publishes nothing on that release (see Publishing on some releases).

A node returns nothing: the output is the parameter, never the return value.

#[subscribe(TOPIC, stale_after = "..")] — on a parameter

#[periodic(every = "20ms", on_overrun = Skip)]
fn brake(#[subscribe(SENSOR_RANGE, stale_after = "70ms")] lidar: Cycle<Range>) {
    brake_for(lidar.get().map_or(0.0, |reading| reading.range));
}

One input: the topic, then how old a reading may be before it reads as absent to this node. The parameter's type is Cycle<T> of the topic's payload. Both parts are required on every input; there is no default bound and no node-wide one. A node has as many inputs as it has such parameters. Cycle<Range> is periodic::Cycle<'_, Range> with its lifetime left out.

#[subscribe] is a part of the #[periodic] declaration, which reads it and removes it. It is not an item to import, and #[periodic::subscribe(..)] is refused.

init

use periodic::{periodic, Out};
use robot_topics::{Count, DIAG_COUNT};

/// Cycles this node has run. Built once by `init`, owned by the node for its whole life.
#[derive(Default)]
struct Cycles(u64);

#[periodic(every = "20ms", on_overrun = Skip, init = Cycles::default())]
fn counter(cycles: &mut Cycles, #[publish(DIAG_COUNT)] count: Out<Count>) {
    cycles.0 += 1;
    count.publish(Count { cycles: cycles.0 });
}

Builds the node's state once, before the framework opens any topic. The body takes it by reference — &mut S, or &S for a state it only reads — and it is the one parameter with no marker, wherever that stands in the list.

Limit: the state is not dropped when the framework ends the node. A failed start and a Fault stop both end in process::exit(1), so a Drop on Motors that stops the motors does not run then. A device's safe state cannot rest on Drop.

safety

#[periodic(every = "20ms", on_overrun = Skip, safety, init = Motors::attach())]

Bare flag, here on the drive of your first nodes: this node implements a safety function. Every topic it declares — each input's, and each output's — must then be on a lane that may carry safety data, and one on the Quality-Managed FastLane fails the build. See What safety checks.

#[param(default = .., range = .. ..= ..)] — on a parameter

#[param(default = 42.0, range = 0.0..=200.0)] kp: f32,

A value the shell can change while the node runs, handed to the body by value on every release. See Run-time parameters.

#[serve(ACTION, lease = "..")] — on a parameter

#[serve(DRIVE_TO, lease = "100ms")] goal: &mut Goal<DriveTo, DriveProgress, DriveDone>,

The goal of an action the node serves, lent to the body on every release. At most one per node, and none on a node declared safety. See Actions.

Keys as constants

use periodic::{periodic, Cycle};
use robot_topics::{Twist, CMD_VELOCITY};

/// How long a command stays usable to this node.
const STALE_AFTER: &str = "310ms";

#[periodic(every = PERIOD, on_overrun = Skip)]

}

What the build refuses

Each is refused at the token to change. The texts are the compiler's output, and the build checks each one.

Written The build says
#[subscribe("sensor/range", stale_after = "70ms")] a topic is a typed definition, not a name. Define it once -- `const TOPIC: Topic<Range, SafeLane> = Topic::new("sensor/range");`, with its payload and its lane (`KernelLane`, `SafeLane` or `FastLane`) -- and name the constant here
#[subscribe(SENSOR_RANGE)] input `range` must declare `stale_after = "<duration>"` after its topic: without it there is no answer to "is this data still usable", and the node would act on whatever it was last given
stale_after = "100ms" in the header `stale_after` is written on each input, `#[subscribe(TOPIC, stale_after = "<duration>")]`; every input has its own and there is no node-wide default
#[subscribe(&SENSOR_RANGE, ..)] a topic is named, not borrowed: write `SENSOR_RANGE` here, without the `&`
lane = .. inside #[subscribe(..)] `lane` is not an input key: the lane belongs to the topic and is written in its definition, `Topic<Payload, KernelLane | SafeLane | FastLane>`
a parameter with no marker that is not a reference `range` is not fed by anything: an input is declared on its parameter with `#[subscribe(TOPIC, stale_after = "<duration>")]`, an output with `#[publish(TOPIC)]`, a run-time parameter with `#[param(default = .., range = ..)]`; the one parameter with none of them is the node's state, which is taken by reference and built by `init = <expr>`
#[param(default = 250.0, range = 0.0..=200.0)] kp: f32 `kp`'s default is outside its range, inside rustc's E0080
#[param(default = 300, range = 100..=1000)] on a node declared safety `stop_within_mm` is a parameter of a node declared `safety`; a safety function's configuration is part of its verified build: make it a `const`
two inputs that name one topic, through one constant or two inputs `front` and `rear` name the same topic: a node reads a topic once, inside rustc's E0080
a parameter typed for another payload than its topic's, an input's Cycle<T> or an output's Out<T> rustc's E0308, at the parameter's type
two outputs that name one topic outputs `command` and `twist` name the same topic: a node publishes a topic once, inside rustc's E0080
command.publish(a); command.publish(b); rustc's E0382, use of moved value: `command` : an output publishes once a release
#[publish(CMD_VELOCITY)] command: &mut Out<Twist> `command` is an output, which the body is handed by value: write `command: Out<Twist>`
fn lidar() -> Range `lidar` returns `Range`, and a node publishes through its outputs, not its return value. Declare one on a parameter, `#[publish(TOPIC)] output: Out<Range>`, write `output.publish(value)` where `lidar` returned the value, and remove `-> Range`
publish = SENSOR_RANGE in the header the rewrite for that node, line by line: see Migrating a node
#[cfg(..)] on a parameter a conditional input is not expressible: write each variant as a node function of its own, with its #[cfg(..)] above #[periodic(..)]
#[serve(DRIVE_TO)] goal: &mut Goal<..> `goal` serves `DRIVE_TO` with no lease: write `#[serve(DRIVE_TO, lease = "<duration>")]`. A goal whose client has gone is stopped when its lease runs out, so the lease is what stops the robot, and it has no default
#[serve(DRIVE_TO, lease = "100")] the lease of `goal` is not a duration: write digits and one of `ns`, `us`, `ms`, `s`, as `lease = "100ms"`, inside rustc's E0080
#[serve(..)] on a node declared safety `goal` serves an action, and this node is declared `safety`: a safety function takes no commands through an action's channel, which any process may write
two arguments with #[serve] `second` serves a second action: a node serves one, which `goal` already does
goal: Goal<..>, by value `goal` is the served goal, which the body is lent to act on: write `goal: &mut Goal<DriveTo, DriveProgress, DriveDone>`
active.succeed(r); active.feedback(f) rustc's E0382, borrow of moved value: `active` : succeed ended the goal

One topic as an input and as an output of the same node is allowed: each release reads what an earlier one published.

Node shapes

One node per program, at the crate root: the attribute generates main.

Publishing on some releases

use periodic::{periodic, Out};
use robot_topics::{Range, SENSOR_RANGE};

#[periodic(every = "20ms", on_overrun = Skip)]
fn lidar(#[publish(SENSOR_RANGE)] range: Out<Range>) {
    if let Some(reading) = read_sensor_if_ready() {
        range.publish(reading);
    }
}

// Your driver call goes here: `None` while the sensor has nothing new.
fn read_sensor_if_ready() -> Option<Range> {
    None
}

A release on which the body does not call publish publishes nothing on that output: the topic's sequence does not advance, its readers keep the previous value until their stale_after says it is too old, and the release is not an overrun nor a refused publish. An Out the body never touches on any path is an unused_variables warning; name it _range if that is meant.

What the value costs. Measured on nodes that publish a 65 536-byte payload on the safe lane, built for the target in release and disassembled (built, not run; the build checks these figures):

The output is published Largest stack frame holding the payload
on every release none: the value is built in the shared element (largest frame in the program: 8 272 bytes, in std::io::copy; main is 1 328)
on every other release none: built in the shared element as well (largest frame 8 272 bytes)
two outputs, the second on every other release none: each built in its own element (largest frame 8 272 bytes)

A release that publishes nothing on an output costs nothing on the stack either. Limit: these hold only while the compiler inlines the body into the generated main; a body marked #[inline(never)] holds its payload on the stack. On the kernel lane a publication is always copied, into a slot of the topic in the kernel, and a kernel-lane payload is at most 4 KiB.

Several outputs

use periodic::{periodic, Cycle, Out};
use robot_topics::{DriveState, Odometry, Twist, CMD_VELOCITY, DRIVE_STATE, ODOMETRY};

#[periodic(every = "20ms", on_overrun = Skip)]
fn drive(
    #[subscribe(ODOMETRY, stale_after = "50ms")] odometry: Cycle<Odometry>,
    #[publish(CMD_VELOCITY)] command: Out<Twist>,
    #[publish(DRIVE_STATE)] state: Out<DriveState>,
) {
    let Some(odometry) = odometry.get() else { return }; // both declined
    command.publish(steer(odometry));
    if odometry.moved() {
        state.publish(DriveState { pose: odometry.pose, stopped: 0 });
    }
} // published here: `command`, then `state` when it was handed a value

// Your control law goes here.
fn steer(_odometry: &Odometry) -> Twist {
    Twist::default()
}

Each output is one parameter and one topic, and each is published or not on its own. They are published when the body ends, in the order they are declared, wherever they stand among the other parameters; a served action's status goes after all of them. A refusal on one output does not stop the others, and is counted and reported for that output alone (see NodeError).

What happens
the body publishes state before command both are published in declaration order: command, then state
the body panics after command.publish(..) nothing is published, on either topic
command's lane refuses on 16 releases in a row one ERROR record naming cmd/velocity; state goes on being published
the node cannot start after creating cmd/velocity and drive/state one ERROR record for the reason, then one per output left without a writer, in order

An output is declared, not created, and publish sends nothing at the call: what the body hands its outputs is published at the end of the release, so a half-run release publishes nothing.

With state

use periodic::{periodic, Cycle};
use robot_topics::{Range, Twist, CMD_VELOCITY, SENSOR_RANGE};

/// One control cycle: count the cycles on which the node had to stop.
#[periodic(every = "20ms", on_overrun = Skip, init = 0u32)]
fn brake(
    #[subscribe(SENSOR_RANGE, stale_after = "70ms")] range: Cycle<Range>,
    stops: &mut u32,
    #[subscribe(CMD_VELOCITY, stale_after = "310ms")] command: Cycle<Twist>,
) {
    let clear = range.get().is_some_and(|range| range.range > 0.3);
    let commanded = command.get().is_some_and(|twist| twist.linear.x != 0.0);
    if commanded && !clear {
        *stops += 1;
    }
}

The state is the parameter with no marker: first, last, or between two inputs as here. The inputs are handed over in the order they are written.

Several inputs of one payload type

use periodic::{periodic, Cycle, Out};
use robot_topics::{Distance, Range, ESTIMATE_DISTANCE, RANGE_CENTRE, RANGE_LEFT, RANGE_RIGHT};

/// The nearest obstacle any of three sensors sees; zero while any of them is silent.
#[periodic(every = "20ms", on_overrun = Skip, init = [false; 3])]
fn nearest(
    #[subscribe(RANGE_LEFT, stale_after = "70ms")] left: Cycle<Range>,
    #[subscribe(RANGE_CENTRE, stale_after = "70ms")] centre: Cycle<Range>,
    #[subscribe(RANGE_RIGHT, stale_after = "70ms")] right: Cycle<Range>,
    was_usable: &mut [bool; 3],
    #[publish(ESTIMATE_DISTANCE)] nearest: Out<Distance>,
) {
    let sensors = [&left, &centre, &right];
    for (sensor, was_usable) in sensors.iter().zip(was_usable) {
        let usable = sensor.get().is_some();
        if *was_usable && !usable {
            println!("nearest: lost {}", sensor.topic()); // the binding, not the parameter
        }
        *was_usable = usable;
    }
    let range = |sensor: &&Cycle<Range>| sensor.get().map_or(0.0, |range| range.range);
    nearest.publish(Distance { metres: sensors.iter().map(range).fold(f32::INFINITY, f32::min) });
}

Three topics of one type, each its own definition (Topic<Range, SafeLane>), each with its own bound.

This builds with no warning. The parameter called right receives the left sensor's readings and is judged by the left sensor's bound. What an author has:

  • Cycle::topic() answers the name of the topic the parameter is bound to: right.topic() is "range/left" here. Report an input by that, never by the parameter's name.
  • A test that times each topic. Silence each topic's publisher in turn and time the node's reaction against that topic's own bound. A test that only checks which name the node reported passes on exchanged bindings. The tree's own is periodic_same_typed_inputs (bounds 70, 330 and 590 ms at a 20 ms period): on QEMU raspi3b, over five runs, the three inputs were dropped 83 to 100 ms, 341 to 350 ms and 602 to 609 ms after their topic's last publication. With equal bounds in a body that treats both inputs alike, an exchange changes nothing observable.

    every = "50ms",

The monitor watches the topics its components already publish and publishes a permit only while every one of them is usable. The drive node takes the permit as a third input:

#[periodic(every = "20ms", on_overrun = Skip, safety, init = Motors::attach())]
fn drive(
    motors: &mut Motors,
    #[subscribe(CMD_VELOCITY, stale_after = "310ms")] command: Cycle<Twist>,
    #[subscribe(SENSOR_RANGE, stale_after = "70ms")] range: Cycle<Range>,
    #[subscribe(DRIVE_PERMIT, stale_after = "130ms")] permit: Cycle<Permit>,
) {
    match (permit.get(), command.get(), range.get()) {
        (Some(_), Some(twist), Some(range)) if range.range > STOP_WITHIN => {
            motors.drive(twist);
        }
        _ => motors.stop(), // no permit, no usable command, no usable range, or an obstacle
    }
}

The monitor reads the pose, the range and the command, and publishes the permit that drive reads beside the range and the command.

Permit is pub struct Permit { pub issuer: u32 }, and DRIVE_PERMIT a Topic<Permit, SafeLane>.

Why this shape:

  • One branch for every failure of a component. A component that is late, lost, or never came up is not usable, so no permit is published. The monitor asks get() and nothing else: no latching stop, no health topics, no was_stale().
  • One branch for every failure of the monitor. A monitor that cannot start, is stopped by Fault, or is starved of the processor is silence on drive/permit, which the drive node already acts on as it acts on any absent input.
  • Start-up order does not matter. Before the monitor has seen all three topics it publishes nothing, and the drive node stays stopped.

The drive node's bound on the permit follows the sizing rule: one lost permit tolerated, a 50 ms monitor and a 20 ms drive node give (1 + 1) x 50 + 20 = 120 ms, written half a period off the drive node's grid as "130ms".

An input holds state, not events

use periodic::{periodic, Cycle, Out};
use robot_topics::{Imu, Odometry, Pose, ESTIMATE_POSE, IMU_DATA, WHEEL_ODOMETRY};

#[periodic(every = "10ms", on_overrun = Skip, init = Pose::default())]
fn estimator(
    pose: &mut Pose,
    #[subscribe(IMU_DATA, stale_after = "35ms")] imu: Cycle<Imu>,
    #[subscribe(WHEEL_ODOMETRY, stale_after = "65ms")] odometry: Cycle<Odometry>,
    #[publish(ESTIMATE_POSE)] estimate: Out<Pose>,
) {
    let Some(imu) = imu.get() else { return }; // no usable inertial reading: publish nothing
    pose.heading_mrad += imu.yaw_rate_mrad_s / 100;
    if let (true, Some(wheels)) = (odometry.arrived(), odometry.get()) {
        pose.x_mm = wheels.travelled_mm; // applied once, on the release it arrives
        pose.corrections += 1;
    }
    estimate.publish(*pose);
}

An input is the newest publication on its topic. Publications that arrived since the previous release and were passed over for a newer one are not shown. So:

  • A topic read by an input carries state: a total, a pose, a command. Odometry here is the distance travelled since power-on, not since the last reading, so a total that was passed over is contained in the next.
  • A topic that carries increments must not be read by an input. Of two increments published inside one of the reader's periods, the first is passed over.
  • arrived() applies a measurement once. get() keeps answering with the same total for as long as it stays usable; arrived() is true only on the release that received it.

Measured on QEMU raspi3b (periodic_estimator, five runs): a node every 20 ms reading a total on the kernel lane. Eight totals published one at a time were each applied exactly once, with the node seen to run at least three more releases with the total still usable. Five bursts of six totals published back to back each ended on the burst's last total, in one correction per burst.

Cycle<T>

One input's view of one release. A node is handed one per input.

An input is in one of three states:

State get() was_stale() since_received()
nothing received since the node started None false None
received, and no older than stale_after Some(&T) false Some(age)
received, and older than stale_after None true Some(age)

get() -> Option<&T>

match lidar.get() {
    Some(reading) => brake_for(reading.range),
    None => brake_for(0.0), // absent or stale
}

The reading, if one was received and is no older than this input's stale_after. Stale reads as absent, so the fail-safe branch is the default branch. The comparison is strict: a reading exactly stale_after old is still usable.

copied() -> Option<T>

let reading: Option<Range> = lidar.copied();

The same reading, copied out, for a node that would rather own it. get() lends the framework's one held copy and makes none of its own.

arrived() -> bool

if let (true, Some(wheels)) = (odometry.arrived(), odometry.get()) {
    *travelled_mm = wheels.travelled_mm; // once, on the release it arrives
}

Whether at least one publication was taken at this release. get() answers "is there a usable reading"; this answers "is it a new one".

topic() -> &'static str

if lidar.get().is_none() {
    log::log!(WARNING, "no usable reading on {}", lidar.topic());
}

The name of the topic this input is bound to, as its definition gives it: "sensor/range". The binding itself, where a parameter's name is only its author's claim (see Several inputs of one payload type).

since_received() -> Option<Duration>

if let Some(gap) = lidar.since_received() {
    if gap > Duration::from_millis(40) {
        raise_sensor_warning();
    }
}

How long since a publication last arrived at this node. Not the publication's age — no transport timestamps a publication. None until something is received, and exactly zero on the release a publication arrives: the arrival is stamped with the release's one clock reading and judged against the same one.

was_stale() -> bool

if lidar.was_stale() {
    log::log!(WARNING, "using fail-safe: last reading too old");
}

Whether a reading was received and has aged past stale_after. Only for a node that needs the distinction get() collapses.

Limit: never received is never stale. An input that has received nothing answers false however long the node has run; stale_after judges the age of something received and is not a start-up deadline. A node that acts only on was_stale() never acts on a peer that never came up. Act on get() being None, which covers not yet, lost and never alike.

missed() -> u32

if lidar.missed() > 0 {
    count_dropped(lidar.missed());
}

Publications the lane lost for this input, as seen by this release's reads. Not a running total, and reported on the release whose reads observed the loss.

It is the lane's own count, and the two kinds of lane mean different things by it:

Lane missed() counts A 200 ms node reading a 50 ms publisher
SafeLane publications never delivered to this reader because newer ones overtook them is handed the newest of four and counts the other three, on every release; nothing is wrong
KernelLane publications the topic overwrote before the node read them is handed the newest of four and reports 0: the other three are still in the topic, passed over, not lost. The topic always keeps its newest 8, and up to 20

The kernel-lane row is a host test over that lane's real subscriber and the kernel's own topic state. The safe-lane row is read from that lane's definition of its count and was not measured. FastLane documents the same meaning as SafeLane. Limits:

  • missed() == 0 does not mean the node saw every publication. A publication this release passed over for a newer one is not counted on the kernel lane. This is why a topic that carries increments must not be read by an input.
  • A non-zero missed() is not always a fault. On SafeLane a publisher faster than its reader is counted on every release.
  • A KernelLane input counts loss from the moment it opened. What was published before it opened is neither handed over nor counted.

rejected() -> u32

if lidar.rejected() > 0 {
    count_rejected(lidar.rejected());
}

Publications the transport refused on this input since the previous release. Not a running total. Only the zero-copy lanes refuse at read, a publication they find malformed; the next release reads again. On FastLane a frame that fails validation is counted again on every release until its writer replaces it. On KernelLane it is always 0: a writer of another payload is refused when it opens, not when its publication is read (see "Payloads").

overruns() -> u32

if lidar.overruns() > 0 {
    hold_last_command();
}

Releases the node missed since its previous cycle ran. One count for the node, the same on every input's Cycle of a release: read it from any one of them, and do not sum it. Delivered once, then cleared. The framework writes each overrun to the system log itself, naming the node, so read this to react to it — logging it again records the same overrun twice.

is_healthy() -> bool

if !lidar.is_healthy() {
    raise_degraded();
}

No loss, no rejection, no overrun, for this input on this release. The one-call form of the three above.

Cycle is deliberately not Send: moving one across threads is a compile error. A node's inputs are opened and read on the one thread that runs it. A KernelLane end belongs to its process and could be used from any thread of it; whether the SafeLane and FastLane ends can is not yet established, so nothing of an input leaves its thread.

What stale_after guarantees

#[subscribe(SENSOR_RANGE, stale_after = "70ms")] range: Cycle<Range>,

Age is measured from receipt at this node, on the clock the cadence runs on. A reading the body acts on was received no more than stale_after ago, and so was published no earlier than stale_after plus the previous sampling gap ago. That gap is one period in steady state.

Limits:

  • After a late wake-up the gap is the whole delay, and that release is not told so. The drive node (every 20 ms, command bound "310ms") is kept off the processor for one second, during which its planner publishes a last command and dies. The first release after the stall is handed that command as received now — since_received() is zero, arrived() is true, overruns() is zero — and the node drives on it for 310 ms more. The releases it missed are reported by overruns() on the release after.
  • A bound shorter than the node's period is accepted. every = "20ms" with stale_after = "5ms" and a 40 ms publisher: the input is usable on the release a publication arrives and stale on the next, for ever.
  • Nothing checks the sizing rule below.

Sizing stale_after

stale_after >= (lost publications tolerated + 1) x the publisher's period + this node's period

and never a multiple of this node's period: write it half a period off.

The age a node observes is a whole number of its own periods, give or take wake-up jitter, so a bound on a multiple is decided by microseconds. "60ms" on a 20 ms node: a reading received at one release is 60 ms old three releases later, a few microseconds more or less, and whether it is still usable there depends on which of the two wake-ups ran later. "70ms" decides it 10 ms clear of any release.

Input Publisher Tolerates Rule Written
range of the 20 ms drive node every 20 ms 1 lost 2 x 20 + 20 = 60 "70ms"
permit of the 20 ms drive node every 50 ms 1 lost 2 x 50 + 20 = 120 "130ms"

A node reacts at a release, so it drops an input between stale_after and stale_after plus two periods after the publisher's last publication, scheduling delay aside: it counts from the release that received the publication and judges at a release.

Run-time parameters

A value you tune while the node runs -- a gain, a limit, a flag -- is a run-time parameter. Declare it on the argument that receives it, with its default and its range:

#[periodic(every = "5ms", on_overrun = Skip)]
fn balance(
    #[subscribe(IMU, stale_after = "12ms")] imu: Cycle<Imu>,
    #[param(default = 42.0, range = 0.0..=200.0)] kp: f32,
    #[param(default = 1.5, range = 0.0..=20.0)] kd: f32,
    #[publish(MOTOR_COMMAND)] command: Out<MotorCommand>,
) {
    command.publish(match imu.get() {
        Some(imu) => MotorCommand::torque(kp * imu.pitch + kd * imu.pitch_rate),
        None => MotorCommand::STOP,
    });
}
  • The argument's name is the parameter's name, at most 23 bytes; its type is one of bool, i32, i64, u32, u64, f32, f64, written as the type itself. range names both ends and includes them, and is required for every kind but bool, which takes none: #[param(default = false)] armed: bool. The default and the bounds may be named constants, and are checked when the node is built. At most 16 parameters per node.
  • The body is handed each value by value, on every release; reading one costs nothing.

  • The node checks every request, against its declared range, exactly, both ends included: a value outside it, a NaN, or a name it does not declare is refused and nothing changes, whoever sent it. param refuses the same way before it sends.

What it costs and what it takes:

  • One non-blocking read per release, of the node's request topic, between the sampling and the body; almost always it finds nothing. A release that finds a request also checks at most 16 values and publishes the node's state. All of it is inside the cycle the overrun accounting measures.
  • Two kernel-lane topics per node with parameters, <node>/__params (its state) and <node>/__param_set (requests): count them in the image's [topic] budget, two table entries and 2 pages for a node of up to two parameters, 8 at 16.
  • When they cannot be opened -- the topic storage is used up, or a recorder still holds the topics of a previous life with another table -- the node runs on its defaults, unsettable, and says so once, before its first release, at WARNING:

  • Run a settable node whose timing matters from the RFS, not from FAT. Its request-handling code is first executed when it handles its first request, and a node loaded from FAT faults those pages in from the file system inside that release.
  • Any program can set a parameter, within its declared range, by writing the request topic, as any program can publish any kernel-lane topic today; a value outside the range never reaches a body. A named topic has no writer authorisation yet.

Actions

A request that takes many releases -- "drive to (2.0, 0.5)", "home the arm", "dock" -- is an action. A client sends a goal; the node accepts or refuses it at once, reports feedback on every release, and ends it with a result. The client can cancel it, and the node stops it on its own when the client is gone.

Define the action once, in a crate both ends import:

use periodic::Action;
use wire_plain::WirePlain;

/// Where to drive, in the `odom` frame [m].
#[derive(Clone, Copy, Debug, Default, PartialEq, WirePlain)]
#[repr(C)]
pub struct DriveTo { pub x: f64, pub y: f64 }

/// How far the base still has to go [m].
#[derive(Clone, Copy, Debug, Default, PartialEq, WirePlain)]
#[repr(C)]
pub struct DriveProgress { pub remaining_m: f64 }

/// Where the base stopped, in the `odom` frame [m].
#[derive(Clone, Copy, Debug, Default, PartialEq, WirePlain)]
#[repr(C)]
pub struct DriveDone { pub x: f64, pub y: f64 }

/// Drive the base to a point.
pub const DRIVE_TO: Action<DriveTo, DriveProgress, DriveDone> = Action::new("drive_to");

Action::new refuses, where the definition is written, a payload that is not a record, a goal larger than 4072 bytes, a feedback and a result that together pass 3920 bytes (each rounded up to 8), and a name longer than 246 bytes.

Serving it

A node serves an action on one more argument, with its lease:

#[periodic(every = "20ms", on_overrun = Skip)]
fn drive(
    #[subscribe(ODOMETRY, stale_after = "50ms")] odometry: Cycle<Odometry>,
    #[serve(DRIVE_TO, lease = "100ms")] goal: &mut Goal<DriveTo, DriveProgress, DriveDone>,
    #[publish(CMD_VELOCITY)] command: Out<Twist>,
) {
    let (Some(mut active), Some(odometry)) = (goal.active(), odometry.get()) else {
        // no goal, cancelled, client gone, or odometry stale: stop
        return command.publish(Twist::default());
    };
    let target = *active.goal();
    let here = odometry.pose.position;
    let remaining_m = (target.x - here.x).hypot(target.y - here.y);
    if remaining_m < ARRIVED_WITHIN_M {
        active.succeed(DriveDone { x: here.x, y: here.y });
        return command.publish(Twist::default());
    }
    active.feedback(DriveProgress { remaining_m });
    command.publish(steer_towards(odometry, &target)) // your control law
}

The goal's status, its feedback included, is published after every output of the release.

Goal / ActiveGoal Meaning
goal.active() -> Option<ActiveGoal> The goal this release runs, or None: idle, or the goal was cancelled, its client is gone, or a newer goal of its client replaced it. The same collapse Cycle::get makes for a stale input, so the stop is the branch you write anyway
active.goal() -> &G What the client asked for
active.arrived() -> bool Whether this is the goal's first release: reset your controller here
active.feedback(F) This release's feedback; the last call in a release wins
active.succeed(R) Ends the goal with its result. Consumes the handle
active.abort(code) Ends the goal with a code. On the goal's first release the client is told Refused(code): this is how you refuse a goal by its content. Consumes the handle
  • One goal at a time. A goal from another process while one runs is refused Busy, and the running goal is untouched. A new goal from the process that owns the running one replaces it, from the same release, with no release between handed no goal; the old one ends Preempted. There is no queue.
  • Requests are read at the start of a release, after the parameters and before the body, at most eight per release, with no lock and no second thread. A cancel committed before a release stops the goal at that release: its body is handed None, and the stop is what it publishes on that release.
  • The status follows the outputs. The node publishes one status per release, idle included, after all its outputs, so a client that sees a goal stopped knows the stop went out first.
  • A node declared safety cannot serve. Any process can write an action's request topic, so a safety function does not take commands through one. #[serve] on a safety node fails the build.

Sending a goal

A program sends a goal in one line:

let done = DRIVE_TO.send(DriveTo { x: 2.0, y: 0.5 })?.wait()?;

With feedback and cancel:

let mut drive = DRIVE_TO.send(DriveTo { x: 2.0, y: 0.5 })?; // accepted, or Err(Busy | Refused(code) | NoServer ..)
while let Some(progress) = drive.feedback() {               // one per server release; None once it has ended
    println!("{:.2} m to go", progress.remaining_m);
    if bumper_pressed() {
        drive.cancel()?;                                     // returns once the server has stopped it
    }
}
let done = drive.wait();                                     // Err(GoalError::Canceled) after the cancel
GoalHandle Meaning
ACTION.send(goal) Waits until the goal is accepted or refused. A client may start before its server: it waits up to ten seconds for the server's first status, then sends the goal, once
ACTION.start(goal) Returns at once; the answer comes through poll
poll() -> Progress Never blocks: Pending, Running(Option<F>) with the newest feedback, or Ended(Result<R, GoalError>). Sends the keep-alive when one is due
feedback() -> Option<F> Waits for the next feedback; None once the goal has ended
wait(self) -> Result<R, GoalError> Waits for the end
cancel() Returns once a status shows the goal stopped
dropping the handle Cancels a goal that has not ended

GoalError is Busy, Refused(code), Aborted(code), Canceled, Preempted, Abandoned, Lost (no longer running, and how it ended was not seen), NoServer, WrongDefinition (the server holds another definition of the action) or Topic(..).

A periodic node as a client never blocks: it starts a goal and polls it once per release, and cancels by dropping it.

#[periodic(every = "50ms", on_overrun = Skip, init = Patrol::default())]
fn patrol(
    #[subscribe(SENSOR_RANGE, stale_after = "120ms")] range: Cycle<Range>,
    patrol: &mut Patrol, // holds drive: Option<GoalHandle<DriveTo, DriveProgress, DriveDone>>
) {
    if range.get().map_or(true, |reading| reading.range < STOP_WITHIN_M) {
        patrol.drive = None; // dropping a goal that has not ended cancels it
        return;
    }
    let finished = patrol.drive.as_mut().map_or(true, |drive| matches!(drive.poll(), Progress::Ended(_)));
    if finished {
        patrol.drive = DRIVE_TO.start(patrol.next_waypoint()).ok();
    }
}

The lease

The handle keeps its goal alive while it is polled: a keep-alive goes out once per server period. A goal whose keep-alives stop -- its client killed, crashed, hung, or simply not polling -- is stopped by the node when its lease runs out, and ends Abandoned.

  • The lease is required, and must be at least twice the node's period: lease = "39ms" on a 20 ms node does not start, could not start: lease 39ms is shorter than twice the period 20ms.
  • Choose about five periods: lease = "100ms" on a 20 ms node. That rides out a lost keep-alive and a client a period late, and a client node up to four periods slow.
  • A killed client's goal stops within the lease and two periods: at 20 ms and 100 ms, about 140 ms after the client's last keep-alive, plus the releases' lateness. There is no death signal to stop it sooner; the lease covers a killed, a hung and a starved client alike.
  • A periodic client slower than the lease loses every goal. A client node polls once per its own release, so its keep-alives are its period apart: a client at 150 ms against a 100 ms lease sees each goal end Abandoned. Give the server a lease longer than the slowest client's period and one server period.
  • A program that stops polling loses its goal too: let drive = DRIVE_TO.send(goal)?; long_work(); drive.wait() is abandoned during long_work. Poll, or call feedback or wait, while the goal should run.

What it costs and what it takes

  • One non-blocking read per release of the action's request topic, almost always finding nothing, and one status publish of at most 4096 bytes, both inside the cycle the overrun accounting measures. Nothing is allocated and nothing is logged.
  • Two kernel-lane topics per action, <action>/__goal and <action>/__status: count them in the image's [topic] budget, two table entries and the pages of a goal record (24 bytes and the goal) and of a status (176 bytes, the feedback and the result).
  • A serving node whose action topics cannot be opened does not start, naming the action: drive: could not start: action drive_to: drive_to/__goal: topic storage full.
  • Recorded and replayed. Every release-journal record carries the goal its body was handed, so a replay hands each body the goal it ran with and opens no action topic; what the body says of it -- feedback, a result -- is not compared, only the node's output is.
  • Any program can send, keep, cancel or replace a goal by writing the request topic and stating another process's id, as any program can publish any kernel-lane topic today. The lease and the device's own lease stay the stop.

The release journal

Every node with an output publishes, on every release, one record on a kernel-lane topic of its own, <node>/__releases, where <node> is the node function's name: lidar publishes lidar/__releases. The author writes nothing for it, and nothing turns it off. A node with no output publishes none.

 release k:  sleep -> read the clock -> sample the inputs -> publish record k -> body
             -> publish each output, in declaration order
 record k:   k, the clock reading, the overruns delivered, what became of each of release
             k-1's outputs (two bits each: none, declined, published, refused);
             the process that published it;
             per input: arrived, missed, rejected, and the reading if it arrived (zeros if not);
             the values of its run-time parameters, which release k's body is handed;
             release k-1's outputs, end to end in declaration order (zeros for one the body
             did not publish)

It is what a recording of the run (topic record) needs to replay a node exactly. The record of release k is published before the body runs, so a body that panics or hangs leaves the release it ran on behind. Its payload is 32 + M bytes, M the inputs' facts and payloads, 8 bytes per run-time parameter and the outputs' payloads, all rounded up to 8, and at most the kernel lane's 4096 B; its layout identity is the node's declaration identity, over the period, the overrun policy, each input's payload type, each parameter's name and kind, and each output's payload type, in order. A node with more than 16 outputs, or whose record would pass 4096 B, runs without a journal and logs a WARNING saying why. topic list shows it as layout 0x….

What it costs and what it takes:

  • One kernel-lane publish per release, of at most 4096 B, between the sampling and the body. It never waits on a reader, and it is inside the cycle the overrun accounting measures: a journal that made a release late is reported as an overrun.
  • One topic per node with an output, in the image's topic budget: one table entry and the record's pages (one page for a record up to 192 B, two up to 384 B, five at 1 KiB, 20 at 4 KiB). Count it when you size [topic] in tail.build.
  • 4 KiB of stack in every node with an output, journal or not: the buffer each record is built in, held for the node's life beside its inputs' readings.

When it cannot be opened -- the topic storage is used up, the record would exceed 4096 B, or the topic is held with another declaration's shape -- the node runs exactly as it would with one, and says so once, before its first release, at WARNING:

brake: no release journal (topic storage full); this run cannot be replayed

Every node, with an output or not, also publishes its description, <node>/__node, after its journal: one kernel-lane topic per node, and one page for a record up to 192 B (a node of a few inputs and outputs), which node list and node info read (shell tools). Count it in [topic] too. When it cannot be opened, the node runs unlisted and says so once, before its first release, at WARNING:

brake: no node description (topic storage full); node list does not show this node

A node's name must be unique within an image. Two node functions of the same name share one journal topic: a second one of another declaration finds the topic held with another shape, takes that refusal, and runs without a journal. The same program started twice shares one journal too, and its records interleave; each names its process, and a replay refuses them.

A Python node runs its own loop and journals through the same record: its page says how.

Recording and replay

Record a run, then run one node of it again, offline, against exactly what it saw:

tsh> topic record -o /recordings/run7.mcap &        FIRST: before the nodes
tsh> lidar & brake & drive &
     ... the run ...
tsh> brake --replay /recordings/run7.mcap
replay: brake life 1: 2104 releases, 2103 compared, identical
facts: sensor/range: 5 releases without an arrival, 3 missed, 0 rejected; cmd/velocity: 0, 0, 0; 1 overruns
replay: running release 2103, the life's last; its output is in no record

--replay FILE goes at the end of the node's own command line, with --life N after it to pick a later life of the node (a restart during the recording is life 2). Nothing in the node changes: the journal above is what replay reads, and the generated main reads the two options. Replay runs the node's init and then its body once per recorded release, handing each input exactly the reading, the loss counts and the overruns that release was handed, and each run-time parameter the value it was handed, at the recorded clock reading. It opens no topic, publishes nothing and never sleeps, and it compares what the body hands each output with what the node published there, release by release; a difference names the output by its topic:

replay: brake life 1: first divergence at release 2059:
  output cmd/brake byte 0: recorded 00 00 00 00, replayed 9a 99 19 3e
replay: 1 of 2103 compared releases differ

exit 1. What it recomputes with the binary you run are every input's age and staleness and the body, so an edited body or a changed stale_after is a what-if: "would brake have stopped earlier with stale_after = "40ms"?" An input or output of another type, another order, period or policy, or a parameter of another name, kind or order, is refused, naming both declarations; a changed default or range replays.

  • Start topic record before the nodes. A node's journal is whole from its first release only when the recorder is already running; otherwise the replay is refused: life 1 starts at release 37: the recorder attached after brake started. A node faster than every 15 ms can lose its first records even so.
  • The last release runs uncompared. Its output is in no record: the node was stopped, crashed, or the recording ended. Replay says its verdict first, then runs it -- so a body that crashed in the recording crashes the same way in the replay, which is the point.
  • Replay runs init and the body as written. A node that opens a device or calls a driver does so in a replay too: replay such a node only where the device is absent, or replay the nodes downstream of it, whose inputs are its recorded output.
  • What replay cannot see shows up as a divergence, never as a false identical: time read other than through periodic::now() or a Cycle, side effects other than the outputs, the node's own command-line arguments (give the same ones), anything depending on HashMap order.
  • A node with no output cannot be replayed: there is nothing to compare, and it is refused before its init runs. Neither can one whose journal the recorder lost: a lost stretch is replayed up to, and the rest is not claimed.

Refusals are on standard error and exit 1 (a malformed --replay ... tail exits 2); the verdict is on standard output.

Start-up

Check every duration, open the outputs, the inputs, the action channel and the journal, drop what the inputs held, then run each release on the grid.

A node opens every topic it declares, and does not run until all are open. An application writes no retry loop and no start-up ordering.

  • The outputs first, in the order written, so two nodes that read each other both start: each creates its topics before it waits for the other's.
  • A served action after the inputs, its goal reader before its status writer, so a client, which sends only once it has read a status, never sends to a reader that does not exist yet. A refusal fails the start, naming the action: serving it is what the node is declared for (see Actions).
  • The release journal, and then the node's description, last: the journal for a node with an output (see The release journal), the description <node>/__node, which node list reads, for every node. Opened after everything the node declares, neither ever takes a table entry one of the node's own topics needs, and neither, refused, stops the node.
  • One budget for the whole node: 2 000 "nobody publishes this yet" answers, 5 ms apart. Ten seconds, whatever the number of inputs. Only that answer is waited on; any other refusal ends the start at once.
  • Nothing published before the node starts reaches it. What each input collected during admission is dropped, and loss from before the start is not reported. Release 0 therefore shows nothing published before the start, on any node, in any start order.

Measured on QEMU raspi3b, five runs each; nothing ran on real hardware:

Test What ran Result

periodic_multi_input a node with a kernel-lane and a safe-lane input, started before its publishers and after them reached steady state in both orders; the first range it showed was one published after it started

Limits:

  • A node does not run until every topic it declares is open. The drive node with no lidar: ten seconds, one ERROR record, exit status 1, and its body never ran. What tells the rest of a system that a node is not running is silence on the topic it publishes.
  • A kernel-lane input never fails the start for absence. Subscribing creates the topic, so a kernel-lane topic nobody publishes, or one whose name is misspelt, is not a start-up failure: the node starts and that input is absent for ever. The topic its open created goes with it when the node ends.
  • A kernel-lane input opened early holds nothing while the node waits. It is opened in the order written, so it may wait ten seconds for a later input's publisher. The topic keeps what is published meanwhile, and the start drops it in one read.
  • Only the first missing topic is named. Three safe-lane publishers down: three ten-second runs to learn all three.
  • An output created before a failed start stays without a writer. A downstream node is admitted against it and receives nothing. The failed node names it, one record per output created. On KernelLane the topic goes with its last end, so once no reader holds it, a restarted node can create it again.
  • A publication that lands between an input's drop and the first release's sampling is handed over at release 0. What holds at release 0 is that nothing published before the start is shown. Beside a publisher that is running, an input can show a reading there.
  • A topic published once, or only when its value changes, cannot be an input. A node that starts after the publication never receives it.
  • A mistyped duration is a start-up failure, not a build failure. See Durations.

OverrunPolicy

Skip

#[periodic(every = "20ms", on_overrun = Skip)]

Abandon the missed releases, resume on the grid. Preserves phase. The default choice for a control loop, where a late command computed from stale inputs is worse than none.

CatchUp

use periodic::{periodic, Out};
use robot_topics::{Count, DIAG_COUNT};

#[periodic(every = "20ms", on_overrun = CatchUp, init = 0u64)]
fn odometer(ticks: &mut u64, #[publish(DIAG_COUNT)] count: Out<Count>) {
    *ticks += 1;
    count.publish(Count { cycles: *ticks });
}

Run the missed releases back to back until caught up. Preserves count. For an integrator or accumulator that must see every interval exactly once.

Fault

use periodic::{periodic, Out};
use robot_topics::{Range, SENSOR_RANGE};

}

// Your driver call goes here.

}

Stop the node and report. For a node whose deadline is the safety requirement.

The first cycle to run past its next release is the last. The node writes one ERROR record to the system log, naming itself and the releases that cycle ran past, then exits with status 1. From periodic_fault_stop on QEMU raspi3b:

[    0.218611] [FAIL] periodic overrun_fault: stopped: missed 2 release(s) under on_overrun = Fault

That record is the overrun's only report: the node has no next cycle, so no Cycle ever carries the count. It stays in the node's log ring after the process is gone, so logview -l error still finds it, and the console shows it too, because the BSP's tail.build forwards errors there. Status 1 rather than 0 lets a supervisor tell a missed deadline from a clean shutdown.

Topics and lanes

pub const SENSOR_RANGE: Topic<Range, SafeLane> = Topic::new("sensor/range");
pub const CMD_VELOCITY: Topic<Twist, KernelLane> = Topic::new("cmd/velocity");

A topic's lane is part of its type, written once, in its definition. A node names no lane, and the inputs of one node may be on different lanes. Changing a topic's lane is a change to that one line, and every end follows.

Lane Copies Kernel calls per message Writers May carry data a safety requirement depends on Holds for a reader
KernelLane one in, into the topic's own slots in the kernel, and one out to each reader; payload at most 4 KiB one to publish, one to read up to 4 at once yes the latest value; the topic also keeps its newest 8 publications, and up to 20
SafeLane none four exactly one yes: the writer cannot alter a frame a reader is inside the latest value
FastLane none none exactly one no — Quality Managed only the latest value

Choose the one with the least machinery that meets the requirement:

The topic Lane
has more than one writer KernelLane, the only lane that allows it
carries a small payload KernelLane
carries a large payload, and a reader has a safety requirement SafeLane
carries a large payload, and nothing downstream is safety-rated FastLane

Zero-copy is not "the fast one, always". For a small payload the copy costs less than establishing a shared region; the crossover is roughly 2 KB, an estimate that has not been measured on either side. The kernel lane carries nothing above 4 KiB: a typed end over it does not compile.

A definition is a constant expression. It can be written out where it is used — #[subscribe(Topic::<Health, KernelLane>::new("health/drive"), stale_after = "125ms")] compiles — but the other end of that topic then has nothing to import.

What safety checks

use robot_topics::{Range, Twist, CMD_VELOCITY};

/// A scan for a viewer, on the lane that is Quality-Managed only.
const DEBUG_SCAN: Topic<Range, FastLane> = Topic::new("debug/scan");

#[periodic(every = "20ms", on_overrun = Skip, safety)]
fn drive(
    #[subscribe(CMD_VELOCITY, stale_after = "310ms")] command: Cycle<Twist>,
    #[subscribe(DEBUG_SCAN, stale_after = "70ms")] scan: Cycle<Range>,
) {
    let _ = (command.get(), scan.get());
}

error[E0080]: evaluation of constant value failed
   |
   |     #[subscribe(DEBUG_SCAN, stale_after = "70ms")] scan: Cycle<Range>,
   |                 ^^^^^^^^^^ the evaluated program panicked at 'input `scan` is on a Quality-Managed lane, and this node is declared `safety`: a safety node reads only from lanes that may carry safety data'

FastLane is Quality Managed by its own design: its writer holds a standing read-write mapping of every slot for the region's lifetime, so it can alter a frame a reader is parsing. That is detection, not prevention.

safety checks the topics a node declares: its inputs and its outputs. A safety node that declares one on FastLane does not build, and the error is at that topic. Limits:

  • An end a node opens itself is not checked. A safety node that opens periodic::subscriber(&DEBUG_SCAN) in init and reads it in its body builds with no error, and its decision rests on a fast-lane topic. So does one that opens a transport directly.
  • Under cargo check only the attribute's refusal shows. A call of the library's entry point written by hand, without the attribute, is refused too, but only by a full build.

What is not detected

Two ends opened through one definition cannot disagree on the lane or the payload. That reaches exactly as far as the shared definition does:

  • Two definitions of one name. One program writes Topic<Twist, KernelLane> and another Topic<Twist, SafeLane>, both for "cmd/velocity": the kernel-lane subscriber starts at once and receives nothing, with no error anywhere.
  • Across languages. A Python topic is a separately written definition by construction, so the same silence is possible there.
  • Two definitions of one name over two payloads that differ. Caught on every lane, whether the two differ in size or only in layout -- a field renamed, retyped or moved, a named value renumbered: every lane refuses the second end at open, so its node does not start, and the record says what the topic carries (see Payloads). Two payloads with one layout under two names (Point and Vector3) are one payload to every lane.

Raw ends

use periodic::{KernelLane, Lane, TopicError};
use robot_messages::geometry::Vector3;
use robot_topics::{Twist, CMD_VELOCITY, SENSOR_RANGE};

/// A raw end kept in a struct names its lane again.
struct Stand {
    commands: <KernelLane as Lane>::Publisher<Twist>,
}

fn main() -> Result<(), TopicError> {
    // The lane and the payload come from the definition: nothing here names either.
    let mut stand = Stand { commands: periodic::publisher(&CMD_VELOCITY)? };
    let mut readings = periodic::subscriber(&SENSOR_RANGE)?; // NotFound until `lidar` runs

    let ahead = Vector3 { x: 0.2, y: 0.0, z: 0.0 };
    stand.commands.publish(&Twist { linear: ahead, ..Twist::default() })?;
    if let Some(reading) = readings.read() {
        println!("{} m", reading.range);
    }
    Ok(())
}

periodic::publisher(&TOPIC) and periodic::subscriber(&TOPIC) open an end of a topic that is not a node's input or output: a test stand, or a pilot that reads or feeds a node's topic. The end is the lane's own, opened from the definition, so it cannot choose another lane or another payload.

A node does not need one to publish a second topic: it declares a second output, which is admitted with the node, named if the node cannot start, checked by safety and recorded for replay, none of which a raw end is:

use periodic::{periodic, Out};
use robot_topics::{Count, Range, LIDAR_SCANS, SENSOR_RANGE};

#[periodic(every = "20ms", on_overrun = Skip, init = 0u64)]
fn lidar(
    scans: &mut u64,
    #[publish(SENSOR_RANGE)] range: Out<Range>,
    #[publish(LIDAR_SCANS)] diagnostics: Out<Count>,
) {
    *scans += 1;
    range.publish(Range { stamp_ns: periodic::monotonic_ns(), range: 4.2, ..Range::default() });
    diagnostics.publish(Count { cycles: *scans });
}

Limits:

  • A raw end does not retry its open. Admission belongs to a node. A raw subscriber on a SafeLane or FastLane topic answers TopicError::NotFound until a publisher exists.
  • A raw kernel-lane subscriber is a reader of its own. Opened beside a declared input on the same topic, or beside another raw end, it is handed every publication, and so is the other end. Unread, it holds its end record and nothing else.
  • A raw publisher is not named in a failed-start record, and is not covered by safety or by replay. A node's second topic belongs in a second output.
  • Never open a second raw publisher on a FastLane topic the process already publishes. Nothing stops it, and publishing on both corrupts the topic.
  • A raw end kept in a struct spells its lane again, as Stand does. If the definition's lane changes that line stops compiling, so the repeat cannot disagree silently.
  • Python has no raw end.

Durations

use std::time::Duration;

const PERIOD: &str = "20ms";

Limit: a duration is checked when the node starts, not when it is built. Payloads

Use a standard payload when one fits: robot_messages has geometry::{Vector3, Point, Quaternion, Pose, Twist}, sensor::{Range, Imu} and navigation::Odometry, with the field names robotics code commonly uses (position, orientation, linear, angular), SI units in each field's doc comment, and a stamp_ns field as the record's time stamp (nanoseconds since boot: periodic::monotonic_ns() at the hardware boundary, periodic::now() in a node that decides, so a replay reproduces it). A Python node reads the same payload through tail_messages, generated from these structs by the build.

Declare your own as a #[repr(C)] struct that derives WirePlain:

use wire_plain::WirePlain;

/// What the balance controller knows at the end of a cycle.
#[derive(Clone, Copy, Debug, Default, PartialEq, WirePlain)]
#[repr(C)]
pub struct BalanceState {
    /// When the cycle ran [ns since boot, monotonic counter].
    pub stamp_ns: u64,
    /// Tilt from upright [rad].
    pub tilt: f32,
    /// Tilt rate [rad/s].
    pub tilt_rate: f32,
    /// Commanded wheel speed [rad/s].
    pub wheel_speed: f32,
    /// Cycles the node has run.
    pub cycle: u32,
}

That is the whole of a payload definition, written once, beside the topic's definition, and imported by both ends. A crate that holds it, its topic and a node builds with #![forbid(unsafe_code)]. field and type names no generated language reserves the generated definitions are printed from this struct

A field's doc comment is part of the payload: its unit is written there, in square brackets, and reaches the generated Python as a comment. An integer field may name its values: #[wire_plain(values(ULTRASOUND = 0, INFRARED = 1))] gives the struct Range::ULTRASOUND and Range::INFRARED, typed as the field.

Two ends must hold one definition, and are checked. The derive describes the layout, and its 32-bit identity -- FNV-1a over field names, their order, their types, nesting, array lengths and named values -- travels with the topic. On every lane an end whose identity differs is refused at open and its node does not start. The kernel lane also says what the topic carries:

drive: could not start: topic `cmd/velocity` refused the open: this is not the payload type the topic carries: it carries 48-byte payloads of layout 0x38793118

That is the record of a node whose Twist has linear and angular exchanged, against a pad that made the topic with the standard one. The system log keeps 96 bytes of a periodic record, so logview shows it cut after "the payload type the", before the shape; the console and the NodeError carry all of it. On the safe and fast lanes the reason ends at "carries". The type's name, the doc comments and the lane are not compared.

A kernel-lane topic lives while an end holds it, so a corrected definition is not refused for ever: once every end of the old payload has closed, the corrected one creates the topic anew.

Frames and transforms

"Where is the obstacle relative to the wheels?" A robot's coordinate frames are declared once, when the program is built, with frames! from the crate frames; a lookup gives the transform between any two of them; the standard geometry records of robot_messages carry the arithmetic. Application code holds no frame index, no frame string, no sign convention and no trigonometry: a conversion is one line.

BASE_LINK moves in ODOM by odometry, and RANGE_FRONT is mounted on BASE_LINK 0.10 m forward, turned 15 degrees.

Four files in the BSP's app/ directory: the frames and the topics, each defined once, and two programs that convert the range sensor's reading.

A topic's doc comment names the frame its numbers are in, by a link to the frame constant. The link spells the path because robot_topics.rs does not import the frames: an import used only by a doc link is an unused import to the compiler, which #![deny(warnings)] refuses. Each program includes both files by #[path], so crate::robot_frames is the same module in every program. The link is a reading aid, which rustdoc renders: nothing checks that a node converts a topic's readings through the right frame.

Through a mount

// app/obstacle/src/main.rs

#![forbid(unsafe_code)]
#![deny(warnings)]

#[path = "../../robot_frames.rs"]
mod robot_frames;
#[path = "../../robot_topics.rs"]
mod robot_topics;

use periodic::{periodic, Cycle, Out};
use robot_frames::{BASE_LINK, RANGE_FRONT, ROVER};
use robot_topics::{Point, Range, OBSTACLE, SENSOR_RANGE};

// "Where is the obstacle relative to the wheels?"
#[periodic(every = "20ms", on_overrun = Skip)]
fn obstacle(
    #[subscribe(SENSOR_RANGE, stale_after = "70ms")] range: Cycle<Range>,
    #[publish(OBSTACLE)] obstacle: Out<Point>,
) {
    let Ok(ranger_in_base) = ROVER.lookup(BASE_LINK, RANGE_FRONT) else { return };
    let Some(point) = range.get().and_then(Range::point) else { return };
    obstacle.publish(ranger_in_base.transform_point(point));
}

lookup(target, source) returns T_target_source, the transform that takes coordinates in source to coordinates in target; the target comes first, as in the transform's name. It walks both frames up the tree to where they meet and composes the links it crosses: at most N - 1 of an N-frame set, with no allocation, no lock and no clock. A lookup between frames joined by mounts always succeeds, and range.get()?.point()? is None when the reading is absent, stale, or not a measured distance. For the 4.2 m reading (an f32) the obstacle is at (4.156888286178356, 1.087039940064772, 0) in base_link: 4.2967 m away, 14.65 degrees to the left.

Across a moving link

// app/obstacle_odom/src/main.rs

#![forbid(unsafe_code)]
#![deny(warnings)]

#[path = "../../robot_frames.rs"]
mod robot_frames;
#[path = "../../robot_topics.rs"]
mod robot_topics;

use periodic::{periodic, Cycle, Out};
use robot_frames::{BASE_LINK, ODOM, RANGE_FRONT, ROVER};
use robot_topics::{Odometry, Point, Range, OBSTACLE_IN_ODOM, ODOMETRY, SENSOR_RANGE};

// The same obstacle in odom: nothing is published while odometry is absent or stale.
#[periodic(every = "20ms", on_overrun = Skip)]
fn obstacle_in_odom(
    #[subscribe(SENSOR_RANGE, stale_after = "70ms")] range: Cycle<Range>,
    #[subscribe(ODOMETRY, stale_after = "70ms")] odometry: Cycle<Odometry>,
    #[publish(OBSTACLE_IN_ODOM)] obstacle: Out<Point>,
) {
    let frames = ROVER.with(BASE_LINK, odometry.get().map(|o| &o.pose));
    let Ok(ranger_in_odom) = frames.lookup(ODOM, RANGE_FRONT) else { return };
    let Some(point) = range.get().and_then(Range::point) else { return };
    obstacle.publish(ranger_in_odom.transform_point(point));
}

with(BASE_LINK, ..) supplies the moving link's pose for this release, borrowed from the input. Its age limit is the input's stale_after, applied by Cycle::get(): the framework's one freshness rule, with no second clock in frames. Every lookup that crosses the link is then one of:

Supplied lookup(ODOM, RANGE_FRONT)
None: odometry absent, or older than 70 ms Err(Absent { frame: "BASE_LINK", parent: "ODOM" }), printed no usable pose of base_link in odom
a NaN or infinite position, or an orientation 1 % or more from unit length (all zero included) Err(NotAPose { .. }), printed the pose of base_link in odom is not a rigid transform
a finite position and an orientation less than 1 % from unit length Ok: the orientation normalised to unit length, then composed

So when odometry stops, obstacle_in_odom publishes nothing while obstacle goes on. With base_link at (1, 2, 0) m in odom, turned 90 degrees left, the obstacle is at (-0.0870399400647699, 6.156888286178356, 0) in odom. A second .with(..) supplies a second moving link; a second value for one link replaces the first. Because the view borrows the input, it cannot outlive the release that judged the input fresh.

A mount is a constant

A mount is written in the frame set and never published. A transform published once never reaches a node that starts later: a reader starts at a topic's newest publication, and a node drops what arrived while it was starting. Nor is a mount a #[param], which holds a scalar and which a safety node may not declare. Recalibrating a mount is a rebuild.

NodeError

[   10.704226] [FAIL] periodic upstream: could not start: topic `orphan/input` never appeared

Why a node ended: it could not start, or the overrun policy stopped it after it had been running. Either way the node writes ERROR records to the system log — its name, then one phrase — and exits with status 1. Those two lines are the console of periodic_orphaned_publication on QEMU raspi3b: a node that had created its publication and then waited ten seconds for an input nobody publishes.

The text opens with the phase, so a node that ran for an hour before missing a deadline never reads as one that failed to start. A node that cannot reach its topic says which and why; it does not run forever reading None. Without a log service in the image, the records go straight to the console.

Where a node's records go. The framework registers the node's log ring before its first release, so each record it writes — an overrun, a run of refused publishes, why it stopped — is one write into that ring, which logview -s periodic reads, after the node is gone too. Writing one never makes a cycle wait for the log service. If log_server comes up after the node, the node does not wait for it: its records go to the console until log_server answers, and a thread of the node's own registers the ring within 2 s of the node's start; a record written before then is on the console and not in the ring. Without a log service in the image every record goes to the console.

  • A refused-open record can be cut. Its tail is the transport's own reason. A kernel-lane payload mismatch carries the shape in force, up to 98 bytes: estimator: could not start: topic `imu/data` refused the open: this is not the payload type the topic carries: it carries 48-byte payloads of layout 0x38793118 is 159 bytes and loses the end of the reason, and with it the shape, whatever the names.   • A mistyped-duration record fits while the node's name, the topic and the text are together 36 bytes or fewer. Past that it loses its end, never the key or the start of the topic.
  • "Left without a writer" is said of every output created whenever something after it fails. On the kernel lane, which takes several writers, another writer of that topic may be alive.

Migrating a node

A node that existed before this change does not build until it is rewritten: subscribe, stale_after, lane and publish are no longer header keys, and a node no longer returns what it publishes. The build error is the rewrite.

The compiler prints the edit

#[periodic(
    every = "20ms",
    subscribe = "overrun/raw",
    publish = "overrun/piped",

fn overrun_pipe(raw: Cycle<Tick>) -> Tick {

error: `subscribe`, `publish`, `lane` and `stale_after` are not node keys: a topic is a typed definition that carries its payload and its lane, and each input and each output is declared on the parameter it belongs to. For this node:

           define  const INPUT: Topic<Tick, SafeLane> = Topic::new("overrun/raw");

           write   output.publish(value) where `overrun_pipe` returned the value, and remove `-> Tick`
           remove  `subscribe`, `publish`, `lane`, `stale_after` from `#[periodic(..)]`

Executor

Most nodes never touch this; the attribute drives it. It is public because the cadence is testable without a topic.

Executor::new(clock, period, policy)

Start releasing every period, from now. Fails with StartError::UnusablePeriod if the period is zero or rounds to zero ticks.

let mut executor = Executor::new(clock, Duration::from_millis(20), OverrunPolicy::Skip)?;

run(body) -> u32

Run until the policy stops the node, then return the releases the stopping cycle ran past. The closure receives each cycle's overrun count. Only Fault stops a node, so under Skip or CatchUp this never returns.

The closure's count and the returned one never overlap. Under Skip and CatchUp every overrun reaches the next cycle's closure. Under Fault the first overrun is the stop, so the closure only ever sees zero and the return value is the one place that count goes — which is why it is #[must_use]. A hand-built executor logs neither, so report both, as the attribute does:

let mut executor = Executor::new(clock, Duration::from_millis(20), policy)?;
let missed = executor.run(|overruns| {
    if overruns > 0 { log::log!(WARNING, "lidar: missed {overruns} release(s)"); }
    do_work();
});
// Only Fault gets here.
log::log!(ERROR, "lidar: stopped: missed {missed} release(s) under on_overrun = Fault");
std::process::exit(1);

step(body) -> ControlFlow<u32>

Run one cycle. Returns std::ops::ControlFlow: Continue(()) to run the next, or Break(missed) once the policy has stopped the node — only Fault does — carrying the same count run returns, and #[must_use] for the same reason.

let missed = loop {
    if let ControlFlow::Break(missed) = executor.step(|_overruns| do_work()) {
        break missed;
    }
};

release() / period()

The next release, and the declared period, in clock ticks.

let next = executor.release();

Clock

What the executor sleeps against: now(), ticks_per_second(), sleep_until(deadline). Releases are slept to, never "now + period" slept for — a relative sleep adds each cycle's scheduling delay to the period and never recovers it.

next_release(policy, release, period, now)

Pure function over ticks: how many releases were missed, and where the next one falls.

let (missed, next) = next_release(OverrunPolicy::Skip, release, period, now);

period_ticks(period, ticks_per_second)

A declared period in ticks, or None if it is zero or unrepresentable.

let ticks = period_ticks(Duration::from_millis(20), clock.ticks_per_second())?;
