TAIL OS documentation

TAIL OS is a microkernel real-time operating system written in Rust. It's built for robotics, autonomous vehicles, and other safety-critical systems where timing is a hard requirement, not a nice-to-have.

Version: v0.9.0 · Early preview

Overview

v0.9.0 ships with:

  • Microkernel — only process, memory, scheduling, and IPC run privileged. Drivers and everything else are userspace.
  • Real-time scheduler — 256 priority levels, preemptive, O(1) dispatch, FIFO or Round-Robin policy.
  • Two IPC patterns — synchronous request/reply (Service) and asynchronous publish/subscribe (Topic), both kernel-mediated with read-only delivery.
  • Userspace drivers — UART and SD card (SDHC) on Raspberry Pi 3B.
  • Developer shell (tsh>) — inspect tasks, processes, memory, and drivers.

Applications are ordinary Rust programs built against the TAIL std. They reach the kernel through a small set of wrappers — std::thread, std::process, and the TAIL-specific std::tail_core::* modules for IPC. The API reference and examples below cover the surface an application developer actually calls.

Microkernel

The kernel keeps a small, fixed set of services in privileged mode and pushes everything else out to userspace. Four subsystems sit above a hardware abstraction layer; user applications reach them through a single kernel call interface.

Core services

  • Process management — create and terminate processes, isolate each one in its own address space, assign a unique PID.
  • Memory management — allocate and protect memory, give each process a private virtual address space, support shared memory regions when processes opt in.
  • Thread scheduling — pick the next thread to run on each CPU according to priority.
  • IPC — route messages and service calls between processes.

Processes and threads

A process owns an isolated address space, a PID, and resource limits. A thread is a unit of execution inside a process — threads in the same process share memory but have their own stack and execution context. Concurrent execution lives at the thread level; isolation lives at the process level.

Memory model

Memory is split into kernel space (privileged), user space (per-process, isolated), and explicitly created shared regions. The kernel enforces read / write / execute permissions through virtual memory; an invalid access faults rather than corrupting another process.

Targets

AArch64 (ARMv8-A) — Raspberry Pi 3B and QEMU virt/raspi3b today. Written in Rust, so memory-safety errors that plague C kernels are eliminated at compile time.

Scheduler

The scheduler is priority-based and preemptive. Its decision rule is simple: always run the highest-priority thread that is ready. What makes it suitable for real-time work is that every scheduling step is bounded in time, regardless of how many threads exist.

Policy

  • 256 priority levels (0 = lowest / idle, 255 = highest). New threads start at the default priority, 31.
  • Highest-priority-first with FIFO ordering within a priority — threads run in the order they became ready.
  • FIFO or Round-Robin — system-wide policy. The default is Round-Robin with a 10 ms quantum; switching to FIFO removes time slicing entirely.
  • O(1) dispatch — the next thread is found with a single hardware count-leading-zeros instruction over a priority bitmap, so dispatch latency is constant.

Thread states

A thread is always in exactly one of five states: Init (created, not yet runnable), Ready (waiting for the CPU), Running (executing now), Blocked (waiting on IPC, I/O, a mutex, sleep, or a timeout), or Terminated.

Real-time properties

  • Bounded ready-to-running latency — constant-time dispatch and a fully preemptible kernel keep the worst case computable.
  • Priority inheritance — when a high-priority thread waits on a mutex held by a low-priority one, the holder temporarily inherits the higher priority. The same boost is applied automatically across synchronous IPC calls. This prevents classical priority inversion.
  • Preemptible kernel — syscalls themselves can be preempted, so a long kernel operation doesn't hold off a higher-priority thread. Interrupts stay enabled across syscall execution.
  • SMP — a single global ready queue is shared across CPUs; threads honour a per-thread CPU affinity mask. Only CPU 0 takes the periodic timer tick; secondaries are nudged by reschedule IPIs.
  • Sleep & timeout queues — time-based blocking is sorted by wake deadline; expired entries are woken on every tick.

IPC: Service & Topic

TAIL OS provides two complementary IPC mechanisms: Service IPC for synchronous request/reply and Topic IPC for asynchronous publish/subscribe. Both share one guarantee: the kernel is the sole mediator. Processes never write into each other's memory — every payload is copied once into a kernel-owned buffer and exposed to receivers as a read-only mapping. That single rule is what makes the IPC layer analysable for safety-critical use (designed with ISO 26262 and IEC 61508 in mind).

Shared message pool

Both mechanisms draw from a single tiered pool of kernel-owned buffers — 256 B, 4 KiB, and 64 KiB cells by default, sized for typical message payloads. In certified mode the pool is pre-allocated at boot and never calls into the heap on the IPC hot path, giving you fixed, predictable resource use. A critical service can also reserve guaranteed buffer slots so it never starves under load.

Service IPC — synchronous request / reply

A service is a named endpoint owned by a server thread. A client sends a request and blocks until the reply arrives; the kernel routes the call to the registered server, copies the request into a pool cell, and hands the server a read-only view. Use it for device drivers, system services, and anything RPC-shaped. See the Service IPC API.

  • Bounded queues. Each service has a 16-slot request queue; each process can have at most 8 requests in flight at once.
  • Priority inheritance. While the server handles a request, it runs at the client's priority — a low-priority server cannot hold off a high-priority client.
  • Per-request timeouts. Clients can attach a deadline to any send and get a clean TimedOut error instead of waiting forever.
  • Register fastpath. Requests of 32 bytes or fewer skip the pool and travel in registers; resolve the name once with lookup_service, then fast-send on the returned handle.
  • Clean teardown. If the server thread or process dies, the kernel drains its queue, releases the buffers, and unblocks every waiting client.

Topic IPC — asynchronous publish / subscribe

A topic is a named channel. Any number of publishers send messages to it; every subscriber that was subscribed at publish time gets its own read-only view of the same kernel buffer. Use it for sensor streams, event broadcasting, and data logging. See the Topic IPC API.

  • Fire-and-forget. The publisher never blocks on subscribers. It returns as soon as the kernel has staged the message.
  • One copy, many readers. The kernel copies the payload once and refcounts the pool cell — fan-out to N subscribers stays cheap.
  • Drop-oldest queues. Each subscriber has an 8-slot pending ring. A slow subscriber loses its oldest unread message rather than slowing the publisher or the other subscribers.
  • Non-blocking reads. A subscriber polls with read(); it returns the next message or nothing. Subscribers never stall the publisher.
  • Per-subscriber isolation. A crashed or stuck subscriber can't stall anyone else; the kernel cleans up its buffers on process death.

Picking between them

Reach for Service IPC when you need a reply, a guarantee of delivery, or transactional semantics — driver calls, configuration changes, filesystem operations. Reach for Topic IPC when you have a continuous stream of data and the latest sample matters more than every sample — IMU readings, camera frames, status broadcasts.

API reference — writing an app

A TAIL OS application is an ordinary Rust program. You define fn main(), build it against the TAIL std, and the loader runs it — there is no _start to write and no custom linker script. Compiled apps are placed in the root file system (RFS) image and launched from the tsh> shell by path.

figure · app build and run lifecycle
flowchart LR A["Write fn main()<br/>+ std::tail_core"] --> B["cargo build<br/>TAIL std · aarch64"] B --> C["ELF binary"] C --> D["Place in RFS image"] D --> E["Boot TAIL OS"] E --> F["tsh> run by path"]

The general-purpose surface (std::thread, std::process, collections, formatting, println!) works as you'd expect. The TAIL-specific IPC and process APIs live under std::tail_core::* and are gated behind a feature flag, so a crate that uses them opens with:

main.rs
// Enables the std::tail_core::* modules (service, topic, process).
#![feature(tail_core)]

fn main() {
    println!("Hello from TAIL OS!");
}

Under the hood, every wrapper below is a thin call over the kernel-call (syscall) interface — a small, fixed set of entry points for thread and process lifecycle, memory mapping, IPC send/receive/reply, topic create/publish/subscribe, mutexes, shared memory, sleep, and CPU affinity. The raw entry points are exposed in tail_core::syscall for low-level use, but applications normally call the higher-level wrappers shown here.

Threads & scheduling

Threads run inside your process and share its address space. Use the standard library; the TAIL implementation maps these onto the kernel's thread and sleep calls.

std::thread
std::thread::spawn(f)         // -> JoinHandle<T>; F: FnOnce() -> T + Send + 'static
std::thread::current()       // -> Thread (handle to the running thread)
std::thread::yield_now()     // hand the CPU back to the scheduler
std::thread::sleep(dur)      // block for a std::time::Duration
JoinHandle::join(self)       // -> Result<T, ..>; wait for the thread, take its value
  • New threads inherit the default priority (31 of 0–255); the active policy (Round-Robin by default) is described under Scheduler.
  • std::thread::sleep(Duration::ZERO) and yield_now() both yield to the scheduler.
  • A thread can be pinned to a set of CPUs with tail_core::syscall::syscall_set_thread_affinity(tid, mask), and the current CPU read with syscall_get_cpu_id().

Processes

Spawn other programs from the RFS and wait on their exit codes. These calls are served by the process_manager over Service IPC; the wrappers live in std::tail_core::process.

Service IPC

A server registers a named endpoint and loops on incoming requests; a client sends a typed request and blocks for the typed reply. Messages are described by ServiceRequestData<T> and ServiceReplyData<T>, which hold a pointer + size and (for the reply) an optional error. All of this lives under std::tail_core::service.

service::server
server::create_server(server_name: &str)         // register a named endpoint

server::receive_service_request::<T>(server_name: &str)
    -> Result<(u64, u64, ServiceRequestData<T>, u64), ErrorKind>
    // blocks; tuple = (client_tid, request_type, request, client_pid)

server::reply_to_service_request::<T>(
    server_name: &str, client_tid: u64, reply: &ServiceReplyData<T>)
    -> Result<(), ErrorKind>
service::client
client::send_service_request_and_wait_for_reply::<T, U>(
    server_name: &str, request_type: u64, request: &ServiceRequestData<T>)
    -> Result<ServiceReplyData<U>, ErrorKind>       // blocks for the reply

client::send_service_request_and_wait_for_reply_with_timeout::<T, U>(
    server_name: &str, request_type: u64,
    request: &ServiceRequestData<T>, timeout_ms: u64)
    -> Result<ServiceReplyData<U>, ErrorKind>       // TimedOut on deadline (0 = wait forever)

client::lookup_service(server_name: &str)
    -> Result<u32, ErrorKind>                       // resolve once to a reusable handle

client::send_request_reg::<T, U>(handle: u32, request_type: u64, request: &T)
    -> Result<U, ErrorKind>                         // register fastpath; request must be ≤ 32 bytes
message types
ServiceRequestData::<T>::new(ptr: *const T, size: usize)
    .get_request_message_ref() -> &T

ServiceReplyData::<T>::new(ptr: *const T, size: usize, error: Option<ErrorKind>)
    .get_reply_message_ref()   -> &T

ErrorKind covers the IPC failure modes you'll handle — NotFound (no such service), InvalidInput (e.g. a register request over 32 bytes), and TimedOut, among others.

Topic IPC

Publishers and subscribers attach to a topic by name. publish never blocks; read is a non-blocking poll that returns the next message as a read-only (pointer, size) pair, or None when the queue is empty. These live under std::tail_core::topic.

topic::{publisher, subscriber}
Publisher::new(topic_name: &str) -> Publisher
Publisher::publish::<T>(&self, message: &T)        // copy & stage; returns immediately

Subscriber::new(topic_name: &str) -> Subscriber
Subscriber::read(&self) -> Option<(*const u8, usize)>   // non-blocking; None if empty

A zero-copy "loan" API (write directly into the shared buffer, hand subscribers a borrowed slice) is in design and not part of this release; the copy-based publish/read API above is the supported surface today.

Example — pub/sub over a topic

Publish a value to a named topic and read it back. Because Topic IPC is asynchronous, read() is a non-blocking poll — loop until a sample arrives.

imu_demo/src/main.rs
#![feature(tail_core)]

use std::thread;
use std::time::Duration;
use std::tail_core::topic::publisher::Publisher;
use std::tail_core::topic::subscriber::Subscriber;

const TOPIC: &str = "sensor/imu";

fn main() {
    let publisher = Publisher::new(TOPIC);
    let subscriber = Subscriber::new(TOPIC);

    let sample: u32 = 0xCAFE_F00D;
    publisher.publish(&sample);

    // read() is non-blocking (topic IPC is async); poll until a sample arrives.
    let (ptr, size) = loop {
        if let Some(m) = subscriber.read() { break m; }
        thread::sleep(Duration::from_millis(1));
    };

    let value = unsafe { core::ptr::read_unaligned(ptr as *const u32) };
    println!("received 0x{:08X} ({} bytes)", value, size);
}

Example — service request/reply

A one-shot echo service: a server thread registers an endpoint and replies to a single request, while the main thread sends a request and blocks for the reply. The request and reply are both a u64 here, but any T works.

echo/src/main.rs
#![feature(tail_core)]

use std::thread;
use std::tail_core::service::{server, client};
use std::tail_core::service::service_request::ServiceRequestData;
use std::tail_core::service::service_reply::ServiceReplyData;

const SERVER_NAME: &str = "echo_server";
const REQUEST_TYPE: u64 = 1;

fn main() {
    // Server thread: register a named endpoint, then handle one request.
    let server = thread::spawn(|| {
        server::create_server(SERVER_NAME);

        let (client_tid, _req_type, request, _client_pid) =
            server::receive_service_request::<u64>(SERVER_NAME).unwrap();

        let value = *request.get_request_message_ref();
        let reply = ServiceReplyData::new(
            &value as *const u64, core::mem::size_of::<u64>(), None);
        server::reply_to_service_request(SERVER_NAME, client_tid, &reply).unwrap();
    });

    // Client: send a request and block until the reply comes back.
    let value: u64 = 0xCAFE_BABE_1234_5678;
    let request = ServiceRequestData::new(
        &value as *const u64, core::mem::size_of::<u64>());
    let reply = client::send_service_request_and_wait_for_reply::<u64, u64>(
        SERVER_NAME, REQUEST_TYPE, &request).unwrap();

    println!("echo replied 0x{:016X}", *reply.get_reply_message_ref());
    let _ = server.join();
}

One ordering note: the client must not send before the server has called create_server, or lookup/send returns ErrorKind::NotFound. In real code, gate the client on a "server ready" signal (e.g. an AtomicBool the server sets after registering, with the client spinning on thread::yield_now() until it's set).

FAQ

Is TAIL OS open source?

No — TAIL OS is currently a closed-source preview. Early access is shared for evaluation under agreement; contact us if you'd like to take it for a spin.

Which boards are supported?

Raspberry Pi 3B and QEMU virt (aarch64) today. Cortex-M and RISC-V targets are in progress.

Why a microkernel?

Smaller attack surface, drivers can crash without taking the kernel down, and it's far easier to reason about determinism when the kernel only does three things.

What language do I write apps in?

Rust, against the TAIL std. Apps are ordinary fn main() programs; the IPC and process wrappers live under std::tail_core::* behind the #![feature(tail_core)] gate. See Writing an app.
